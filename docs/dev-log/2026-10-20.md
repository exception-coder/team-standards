# 2026-10-20：让默认流程按目标和风险执行

## 判断与调整

套件已经通过默认开发/交付引导、独立影响判定、测试资产复用、悟道和人话向原则驱动演进。但底层旧规则仍会将局部任务扩张为结构治理，甚至因注释或目录命名中断编辑。4.14.0 将以下冲突收敛到[工程原则](../../plugins/team-standards/skills/change-readiness/references/engineering-principles.md)，沿用现有 Skill，没有新增平台或治理登记。

| 旧要求 | 当前做法 |
|---|---|
| 文件/行数、新类、新表决定档位；发现字段或事件就停止升档 | 按行为、不变量、影响与可恢复性选择深度，只暂停依赖关键未决问题的部分 |
| 超过 80 行必拆；每个新分支建 Service；两个服务调用另建编排器 | 以职责、独立变化、依赖和验证难度判断；允许内聚的原位修改 |
| 注释固定行数，日期/工单号直接判违规 | 说明非显然契约和原因，保留必要法律、兼容及缺陷依据 |
| 统一禁止外键，限制索引数量，强制包装类型/集合工具/手动回滚 | 核对项目、数据库、序列化和事务契约，按真实风险选择 |
| 架构路径、注释 Hook 默认 block | 默认 warn；项目显式 block/off 继续生效，未将提示计为 PASS |
| 流程文档残留固定 phase=all 和 M/L 必建 change | 与开发/交付入口对齐，按影响独立维护规格、设计和验证 |

结构参考由约 460 行收敛到约 60 行，保留语义分包、公开边界、事务与验证依据。历史案例保留教训，更新当前处理方式，不再把旧的 Saga、强拆或注释阈值当作默认规则。CLAUDE、派生 AGENTS、流程图、总览与关联 Forge 架构说明同步。

## 后续维护判断

新增规则先问它保护什么实际风险、现有能力是否已覆盖、能否只作提示；明确可机械证明的约束再考虑项目门禁。复杂能力保持按需加载，不为每个案例新增 Skill、测试文件或检查脚本。后续试点以实际误报、重复执行和未覆盖风险改进，不以规则条数或机器 PASS 衡量效果。
