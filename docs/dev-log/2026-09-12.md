# 开发日志 · 2026-09-12

## 16:00 · 调整流程 · OpenSpec 文档推进与证据检查

**原因：** 工件存在、会话里提到 change 或任务被勾选，均不能证明本次实施有明确设计依据和有效验证。文档推进需要可执行的阶段条件、意见回写、切片归属和恢复入口。

**改动：**

- 复用 change-readiness 与 delivery-verification，加入阶段准出、概设详设、评审职责、暂停取消和交接契约，不新增同义 Skill。
- 增加共享 JSON 检查器及会话绑定、初始脏范围保护、场景/视图/任务映射、代码与文档指纹、显式证据记录和独立 CI 检查。
- 新增 Stop 适配以任务累计两次补齐为上限；默认报告试运行，block 模式替换 OpenSpec 的旧启发式分支。官方 CLI 继续负责工件解析、同步和归档。
- 增加真实 Git、OpenSpec 1.13.0、路径、失效和失败测试；两项原有测试统一文本换行及 Windows 临时目录表示，保持原断言。
- 跨仓发布契约按 LF 规范化文本比较，与存量完整性指纹一致；避免三个仓库的 Git 换行配置差异造成内容相同却无法打包。

**影响：**

- 项目不复制团队规则，不增加必需治理配置；机器记录引用现有正文，不能伪装人工批准。
- 混合文件归属、外部 planning store、多 change 聚合、无 change 的 S 档机械豁免和真实业务宿主验收仍有明确支持边界，不能将本次交付宣传为全场景强制闭环。
- 未启用 OpenSpec 的源码仓库沿用兼容设计流程；本仓开发依据为用户知识库中的实施方案与编码摘要。
