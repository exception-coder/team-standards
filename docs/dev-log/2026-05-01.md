# 开发日志 · 2026-05-01

## 00:27 · 修复规则 · solution-review-required

**原因：** 用户反馈 AI 在项目开发中容易把现有低质量代码当作参考范式，或迎合用户给出的直接实现方案，缺少更高层次的工程审视与主动建议能力。

**改动：**
- 强化 `solution-review-required`：补充“现有代码是事实材料，不是天然正确设计范式”的核心原则
- 新增“评估现有代码是否值得参考”执行步骤，要求区分兼容旧结构和扩散坏结构
- 补充触发场景：参考现有代码、照类似文件、抄云端逻辑、局部补丁绕过状态机或数据一致性
- 同步更新 `AGENTS.md`、`CLAUDE.md`、`README.md`、`docs/skill-flow.md` 的覆盖范围说明
- 递增插件版本：`.codex-plugin/plugin.json` 1.9.0 → 1.9.1，`.claude-plugin/plugin.json` / `marketplace.json` 1.17.0 → 1.17.1

**影响：**
- AI 在用户给出具体方案或要求参考现有代码时，必须先做目标/方案/现有代码质量三方审视
- 低质量旧代码只能提取事实和业务规则，不能作为新实现模板继续扩散
- 风险明显时 AI 必须主动给出更优建议，而不是默认迎合用户表述或代码惯性

## 00:45 · 调整流程 · dev-log

**原因：** 用户确认项目已经使用 git 管理，普通小变更、迭代和版本号递增继续强制写 dev-log 会与 commit body 重复，增加维护成本，容易把 dev-log 变成流水账。

**改动：**
- 将 `dev-log` 从“team-standards 任意变更必写”收窄为“决策型变更才写”
- 明确 commit body 是默认变更日志，普通小改、措辞同步、版本号递增不再写 dev-log
- 保留新增/删除 Skill、触发时机或核心行为变化、规则方向反转、跨 Skill 链路变化、重大团队原则沉淀等场景的 dev-log 要求
- 同步更新 `AGENTS.md`、`CLAUDE.md`、`README.md`、`docs/skill-flow.md`，并创建 skill-flow v17 快照

**影响：**
- 后续 team-standards 普通迭代只需写清楚 git commit body
- dev-log 只承担长期决策背景记录，避免与 git 历史重复
- 重大规则变更仍保留人工可读的演进说明

## 01:14 · 调整流程 · skill-flow

**原因：** 用户发现 `docs/skill-flow.md` 中存在 `superpowers` 外部 Skill（如 `brainstorming`、`writing-plans`、`systematic-debugging`），但当前工程并未包含或使用这些 Skill。继续放在主链路中会让维护者误以为 team-standards 依赖外部插件。

**改动：**
- 从 `docs/skill-flow.md` 的 Skill 总览移除所有 `superpowers` 来源条目
- 从主链路、功能开发链路、Bug 修复链路中删除外部 Skill 节点
- 将文档定位调整为只梳理 team-standards 自身 Skill
- 创建 `docs/skill-flow-20260501-v18.md` 作为链路结构变更快照

**影响：**
- `docs/skill-flow.md` 只描述当前插件工程实际维护的 Skill
- 避免 team-standards 与外部 `superpowers` 工作流发生误绑定
- 后续如需引用外部工作流，应放在“外部可选参考”，不得混入主链路

## 01:37 · 修复规则 · architecture-ddd-lite-fullstack

**原因：** 用户明确提出编码要求：代码结构必须清晰、易于维护、低耦合、高内聚。原 `architecture-ddd-lite-fullstack` 虽然已有高内聚、低耦合方向，但缺少可执行的结构质量门禁，容易停留在口号层面。

**改动：**
- 在 `architecture-ddd-lite-fullstack` 中新增“结构质量门禁”
- 将代码结构清晰、易维护、低耦合、高内聚纳入编码前检查清单和输出要求
- 补充禁止行为：复制低质量旧实现、职责混杂、跨层直接依赖、巨型 Service 等
- 同步更新 `AGENTS.md`、`CLAUDE.md`、`README.md`、`docs/skill-flow.md` 的覆盖范围说明

**影响：**
- AI 编写业务代码前必须显式判断结构质量，而不只判断分层
- 新增实现不得为了快速完成而制造难读、难测、难替换的结构债
- 结构清晰、易维护、低耦合、高内聚成为默认编码门禁
