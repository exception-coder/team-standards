# 2026-08-26 开发日志

## 公共 Skill 第一轮收敛

### 背景

团队工具长期按单点问题新增 Skill，逐渐出现相邻步骤各自成为入口、同一规则在多个文档重复、日常插件被误解为主路由、项目专属能力混入团队插件等问题。用户明确要求减少零散插件，并将项目特有编码规范、脚手架、URL 定位和架构检查归还项目自身。

### 决策

1. `team-standards` 从 34 个公共 Skill 收敛为 21 个，并建立 8 阶段统一工程主流程。
2. 不直接丢弃有价值细则：旧 Skill 正文移动到存活 Skill 的 `references/`，只取消独立发现入口。
3. `design-doc-required` 合并方案审视与实施前代码定位；`bug-doc-required` 合并修复期规则；`markdown-writing-standards` 合并文档索引生命周期。
4. `backend-knowledge-graph-required` 合并反向影响与领域规格挖掘，成为单服务后端事实唯一入口。
5. `init-project-docs` 合并项目文档刷新和项目画像，统一为 init/refresh/status/profile 四模式。
6. 设计治理从五个入口收敛为两个：bootstrap 负责 Registry 与偏好学习，guardian 负责实现与视觉验收。
7. 删除 `arch-lint` 和 `cross-project-locator` 公共入口；具体 Flutter 架构规则和产品生态拓扑由实际项目或拓扑仓维护。
8. `project-coding-profiles` 只保留 `encoding-guard`；模块脚手架和 URL 定位下沉项目。
9. `yoooni-daily-plugin` 将安装、更新合并为 `yoooni-team-tools`，删除业务知识同名转发层，直接调用知识仓内部权威流程。

### 原因

- Skill 应对应稳定的用户意图，不应对应每个内部步骤。
- 多个相邻强制 Skill 会增加漏触发、重复读取和互相矛盾的概率。
- 项目专属规则放在公共插件中会让其他项目误触发，也会造成所有权不清。
- 参考文件按风险渐进加载，可以保留深度而降低默认上下文重量。

### 结果

- 公共插件 Skill 从 45 个降为 28 个：daily 6、team 21、profiles 1。
- 工程链路统一为“证据与设计 → 后端事实/影响 → 代码定位 → 架构编码 → 实施验证 → 回写 → 提交”。
- 破坏性变更使用 Major 版本：`team-standards 2.0.0`、`project-coding-profiles 1.0.0`；daily 继续汇入尚未发布的 `1.0.0` 调整。
- 根目录 README 保留旧入口到新入口/项目归属的迁移表，历史原因不再散落在运行时触发文档中。

## 第二轮归属校正

### 决策

1. `yoooni-onboard-pipeline` 不再属于 Yoooni 日常插件，完整流程和状态脚本并入 `init-project-docs` 的 `onboard` 模式。
2. `yoooni-team-tools` 删除为 Skill；安装、检查和更新保留为仓库维护脚本，避免把维护命令误当用户意图入口。
3. 删除 `yoooni-onboard-init`；新员工资料获取不属于跨项目工程能力。
4. 删除 `yoooni-prod-log-query`；生产日志访问必须由拥有目标系统、权限和脱敏规则的项目维护。
5. README 将编码规范展示为层级：架构门禁 → common 基线 → Java/Dart/LLM 按需叠加，不再把它们误画成平级选择。

### 结果

- `yoooni-daily-plugin` 从 6 个 Skill 收敛为 2 个，只保留 SMB 访问和 Hook 周报。
- 公共插件总量从 28 个降为 24 个；`team-standards` 仍为 21 个，因为 onboarding 被合并为既有 Skill 模式。
- 通用项目初始化拥有单一入口，项目专属生产查询和入职流程回归实际所有者。

## 21:03 · 调整流程 · 跨插件 Hook 契约

**原因：** 三个插件必须独立安装，但共享 Hook 的物理副本和共同写入的 JSONL 会产生漂移风险。直接建立运行时跨插件依赖会破坏独立安装边界，因此选择“副本随插件分发、契约由工作区门禁统一”的治理方式。

**改动：**

- 三份版本陈旧提醒改为同一份自识别实现，并纳入三方字节级检查。
- Hook Event 增加 v1 schema、生产端字段白名单和消费端兼容校验。
- 历史无版本事件继续按 legacy v1 读取，未知版本和非法记录显式计数。
- Skill 审计新增“含文件但缺少 `SKILL.md`”的孤儿目录检查，不把 Git 不跟踪的纯空目录作为 CI 契约。

**影响：**

- team-standards 与 project-coding-profiles 继续独立生产本地事件。
- yoooni-hook-report 不再静默吞掉数据契约漂移。
- release dry-run 会在共享 Hook 或 schema 漂移时阻断发布。

## 22:20 · 修复规则 · SQL 正确性与上下文工具边界

**原因：** AI 生成的多表 SQL 出现未限定字段时，现有 DDL 准备门禁和查询性能门禁都无法发现名称解析错误；缺表和旧 Maven 制品还会依次掩盖后续问题。团队后续同时引入 Graphify 与 OpenSpec，如果继续由 Skill 扫描代码、生成设计和复制规格，会重新形成多套并行流程。

**改动：**

- 在 `backend-knowledge-graph-required` 下新增 SQL 正确性 reference，不新增公共 Skill。
- 增加多数据源字段限定、显式投影、动态 SQL、真实数据库、Mapper 契约和制品 SHA 规则。
- 增加只告警的 SQL 正确性 Hook，覆盖多表简单裸字段和通配投影。
- 明确 Graphify 负责当前实现事实、OpenSpec 负责行为规格与活动变更、Skill 负责意图路由和质量门禁。
- 项目启用 OpenSpec 后，设计入口评审对应 change，不再创建平行设计文档；未启用项目保留兼容路径。

**影响：**

- SQL 正确性、查询性能和发布制品成为三条独立证据链，前序失败不再被误当成完整验证。
- Graphify 与 OpenSpec 不新增团队公共入口，既有 Skill 将逐步从“自产上下文”收敛为“消费权威上下文”。
- 项目特定 DDL、数据库版本、Mapper 分支、OpenSpec schema 和 CI 命令仍由项目自身维护。
