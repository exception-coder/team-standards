# 开发日志 · 2026-04-26

## 修改 Skill · design-doc-required（v1.11.0 → v1.12.0，新增轻量模版分级）

**原因：** 实践中"批量写接口"是常态，但 `design-doc-required` 长期只有一档（完整模版 `template.md` 18 节 + 配套 `coding-template.md` 7 节），单接口跑一遍轻松吃掉几千 token，对"在已有架构内加 endpoint / 调整库表读写"这种小改造严重过度投资。已有的「第四·五步：轻量修订流水」只解决了"文档已存在的小修"，覆盖不到"全新但小范围"的场景；而「合法的例外情况」又把口子开得太大。中间一档明显缺位。

参考 `korepos-refund/docs/业务表变更时序/refund/获取可退商品.md` 的成熟形态：以「库表读写时序图」为主轴，配过滤规则表 + 失败行为表，对单接口设计意图 / 后续库表行为回归同时生效。决定把这个形态直接收编为 design-doc-required 的轻量模版。

  - 第三步「文档不存在时」拆为轻量 / 完整两套引导话术
  - 第二步「文档存在时」加文档类型识别（轻量直接读 / 完整走 coding.md 子流程）

**影响：**

- 已有架构内的单接口新增/调整、库表读写流程描述等"批量写接口"场景走轻量模版，单文档章节数从 18 → 7、不再生成 coding.md，预估 token 占用下降 ≥ 60%
- 完整模版分支保持原流程不变，跨服务 / 新增表 / 复杂事务 / 新增对外契约场景仍按 18 节完整模版 + coding.md 处理
- 滥用风险靠 9 项硬清单兜底（不新增表 / 不新增对外契约 / 不跨服务 / 不引入新中间件 / 不重设状态机等），决策必须显式告知用户「判定为【轻量/完整】，原因：xxx」
- 第一个用例：korepos-refund 后续 backendv2 接口扩展（如 `获取可退商品` 加 `includeMergeTable` 入参那种规模的改动）走轻量模版
- 与既有「第四·五步：轻量修订流水」的边界：轻量修订流水管「文档已存在的小修」（追加调整流水行）；轻量模版管「文档全新但改动小」（用 lightweight-template 生成新文档）。两者互补不冲突
