# 2026-08-27 开发日志

## 08:52 · 调整流程 · Graphify 与 OpenSpec 落地路由

**原因：** `yoooni-one` 实证表明，目录存在不等于上下文链路已就绪：OpenSpec 可以通过结构校验但仍缺少项目上下文和主规格，Graphify 也可能落后未提交工作区数十小时。若 Skill 继续强制自产设计文档和 AI 索引，会与两类工具形成平行事实源。

**改动：**

- `change-readiness` 将可用 OpenSpec change 作为首选设计载体，旧设计文档降为兼容路径。
- `business-logic-orientation` 改为 Graphify 优先的现状理解入口，完整文档化流程下沉为按需 reference。
- `backend-evidence` 固定 OpenSpec 行为、Graphify 实现、DDL/日志运行事实的权威边界。
- `init-project-docs` 将未提交工作区文件版本纳入图谱新鲜度判断。
- 以“真实配置 + 相关 change + 可读 artifacts”定义 OpenSpec 已启用，不再按目录存在判断。

**影响：**

- 已接入 OpenSpec 的项目只维护一套变更 artifacts，不再额外生成团队设计正文。
- Graphify 结果过期时只能用于候选定位，实施必须刷新或用当前源码补证。
- 编码、SQL、数据库、测试与发布制品门禁继续保留，不被上下文工具替代。

## 09:20 · 修复规则 · 上下文机械门禁

**原因：** Skill 已切换到 OpenSpec 与 Graphify 主线，但设计 Hook 仍只认可传统设计文档，后端 Hook 仍只识别 Dart 路径和旧知识卡，造成“语义路由允许、机械门禁误拦”以及过期图谱静默放行。

**改动：**

- 设计依据 Hook 认可包含真实 context 和完整活动 change artifacts 的 OpenSpec 项目。
- 空 OpenSpec 模板、缺 proposal/design/tasks/specs 的 change 继续视为未就绪。
- 后端上下文 Hook 增加 Java/Kotlin 主源码路径，并识别 Graphify query/path/get-node/search。
- Graphify 查询后比较目标文件与 manifest mtime；缺 manifest、未索引或目标更新时输出独立过期提示。

**影响：**

- OpenSpec 项目不再需要占位 `docs/design` 才能通过源码写入门禁。
- 传统知识卡仍可独立使用；选择 Graphify 时必须证明图谱覆盖当前目标版本。
- 默认 warn 保持低干扰，项目可沿用既有 block 模式提高强度。

## 09:47 · 调整流程 · Skill 边界与命名收口

**原因：** Graphify 与 OpenSpec 已成为实现定位和行为变更的权威入口后，`design-doc-required` 与 `backend-knowledge-graph-required` 的旧名称仍暗示团队插件会自产设计正文或代码知识图谱；`init-project-docs` 及项目画像参考也仍复制 Graphify 的执行和全仓扫描步骤。

**改动：**

- 将开发前主门禁更名为 `change-readiness`，继续承担方案审视、风险分档、设计依据和代码定位。
- 将单服务后端入口更名为 `backend-evidence`，聚焦 DDL、SQL、领域语义、运行证据和反向影响。
- `init-project-docs` 从 202 行压缩到约 100 行，Graphify 细节改为调用当前安装 Skill，不再维护平行手册。
- 项目画像改为消费 Graphify 后定向补证，不再手工全仓构建第二套 Entity/Service/Controller 索引。
- Hook、测试、入口和活动文档迁移到新名称，旧环境变量仅作为兼容输入保留。
- Hook Event 支持测试专用输出目录，真实项目验证不再污染团队周报日志。

**影响：**

- 公共 Skill 数量不增加，主流程名称与实际职责一致。
- Graphify 和 OpenSpec 可以独立演进，团队插件不需要同步复制其命令和内部实现。
- 2.0 发布后必须更新并重载三套插件，旧缓存不会自动消失。

## 18:45 · 调整流程 · 移除平行代码事实库

**原因：** `backend-evidence` 虽已声明 Graphify 负责当前实现，但内部仍保留手工反向索引扫描器、四类索引模板和十类代码知识卡；同时工具自检只判断 Codex 缓存目录存在，旧版本也会误报 Ready。名称已经收敛，事实源和运行态仍未真正闭环。

**改动：**

- 删除手工反向索引扫描器、索引模板和代码知识卡模板。
- 状态、字段、事件、API、读写点和调用方改为 Graphify 即时查询，当前变更影响写入 OpenSpec。
- 稳定业务真理继续进入 domain knowledge；DDL、测试、日志和执行计划保留在各自权威系统。
- `glossary-required` 压缩为术语路由，删除独立 glossary 候选池、模板和 onboarding 的 `07_glossary.md`。
- Codex 工具自检改为比较工作区 manifest 与最高缓存 SemVer，版本不一致时明确失败并要求更新、重启。

**影响：**

- 公共 Skill 数量不变，但 `backend-evidence` 的文档和维护面显著缩小。
- 不再要求项目持续维护一套会随源码漂移的手工调用方、读写点和枚举索引。
- 团队成员能够在工具检查阶段发现“源码已升级、Codex 仍加载旧缓存”的真实问题。

## 19:35 · 调整流程 · 项目接入轻量化

**原因：** Graphify、OpenSpec 与领域知识已经分别承担当前实现、目标行为和稳定业务语义后，`init-project-docs` 仍默认维护 Graphify 的六份 Markdown 镜像、00–10 项目说明树和三份画像，形成重复事实源与持续同步负担。

**改动：**

- `init-project-docs` 改为项目上下文接入器，默认输出状态摘要而不创建文档树。
- `refresh` 直接刷新 Graphify/OpenSpec/项目入口；`profile` 仅按需生成一份轻量导航。
- 删除旧项目说明、业务上下文、编码约定和技术卡模板。
- Bug 与变更门禁改为直接查询项目规则、Graphify、OpenSpec、领域知识和运行证据。
- 旧 `00_project_overview.md` 保留只读兼容，不再作为新项目初始化前置。

**影响：**

- Yoooni One 等已接入 Graphify/OpenSpec 的项目无需再维护平行 AI 文档树。
- 项目自有规范留在项目仓，公共插件只负责路由与新鲜度边界。
- 老项目既有文档不会被自动删除，可在迁移期继续作为导航读取。
