# 2026-09-28

## 架构图信息设计入口

- 原因：近期产品能力图、领域图和系统协作图的评审表明，仅有绘图工具和设计文档写作规则，仍容易把角色表画成能力图，或把多个视角混在一张图中；视觉调整不能解决语义错误。
- 决策：新增 `architecture-diagram-design`，先确定每张图回答的问题，再区分主角、层级和阅读路径；产品图展示工作台能力，领域图展示归属，系统图展示协作；实际渲染后核对可读性与文档对应。沿用项目视觉规范与已有 draw.io 工具，不内置固定样式或新绘图引擎。
- 边界：`clear-design-docs` 保持正文及模型表达职责，`business-visualization-advisor` 保持业务指标/看板职责；本 Skill 不把拟建图示视为实现证据，也不新增 Hook 或通用机器门禁。版本升至 4.10.0，团队插件 19 个 Skill。

## 独立设计文档评审入口

- 原因：已有概设/详设写作规范、内容契约和开发前方案审视，但缺少可独立调用、以本期实质问题为中心的设计文档评审方法。个人 `reviewing-design-plainly` 的事实核对与通俗表达可复用，强制开场问卷、两张固定表和再次请求修改许可则不适合团队默认流程。
- 决策：新增 `reviewing-design-plainly`，覆盖概设、详设、技术方案和实施方案的矛盾、关键缺口、待核实前提与过度设计；按本期范围与实际风险分类为必须修正、需要决策、提醒。未来高并发/大数据和冷门场景默认提醒，保留明确切换边界但不预建复杂机制；已承诺指标及安全、数据正确性底线仍须核对。
- 边界：`clear-design-docs` 继续负责清晰表达、对象图和字段说明，内容契约继续负责结构/状态/绑定，`change-readiness` 继续负责已授权开发的就绪审视；新 Skill 不引入 Hook、独立审批或默认文档修改。版本 4.9.3，team-standards 18 个 Skill。
- 场景审读：未承诺高并发的一期单库方案只提示切换边界；已承诺权限隔离却缺服务端约束须修正；冷门业务分支未进入本期时不强制建表或开发；部署前提不影响结论时不先发问卷。这是规则审读，不冒充真实项目评审或人工业务认可。
- 验证：新 Skill 结构、跨引用、三处版本与工作区总览同步、Skill 审计、Agent 入口同步及差异格式检查通过；纯 Skill/文档更新未运行无关运行时测试。
