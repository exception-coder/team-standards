# 文档同步规范

## 确定归属

从项目入口、既有索引和相关链接找到同主题权威文档，优先原位更新。规格、当前设计、操作手册与变更历史分别保留各自用途，不为同一内容另写平行正文。用户指定载体时沿用；已采用的规格或设计流程仍按项目约定执行。

简单修改通常由源码、测试、必要说明和提交承载；不自动新建报告、日报、索引目录、手工代码关系表或 AI 摘要。用户明确要求或确有持续维护用途时再新增文档。

## 同次同步

对照实际 diff 和行为核对 README、接口契约、安装、配置、启动、测试与操作说明，只更新受影响段落；现有多语言说明受影响时同步。没有文档影响时说明具体理由，不制造刷新日期或空标题式改动。

规则、Skill 或工作流变化时同步相关入口和已有导航。生成文件先改其维护源再重新生成，不直接编辑派生产物，也不为同一规则手工维护多份正文。

## 写清楚并验证

- 先说读者要知道的结果或动作，再说明条件和原因；用具体对象与动词，不用术语堆砌替代解释。
- 保留必要技术名词、单位、数值、否定、例外和责任；精简不能改变业务含义或把假设写成事实。
- 区分规划、实现、验证和上线状态，未接入或未运行的能力不能写成已生效。
- 检查标题层级、代码围栏、表格列数、本地链接与实际命令路径；导航只更新受影响的已有入口。
- 图表用于解释关系或流程更清楚时再添加；需要图时使用目标环境支持的语法并验证实际渲染，文本结构检查不能冒充渲染成功。

更新说明和实现作为同一逻辑交付单元，按 [验证](../foundation-verification/SKILL.md) 与 [Git](../foundation-git/SKILL.md) 规范处理；不把新增报告数量当作交付质量。
