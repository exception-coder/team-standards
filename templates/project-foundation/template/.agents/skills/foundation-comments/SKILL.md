# 代码注释规范

代码修改和注释维护一起完成。先理解职责、调用契约及业务约束，再判断应补充什么；不要在没有理解代码时生成看似完整的注释。

## 必要注释

| 对象 | 应说明的内容 |
|---|---|
| 新增业务类、业务模块或对外复用组件 | 职责、适用范围和关键边界；类用类文档，函数式模块使用文件或模块文档 |
| 新增或改变的公共 API、接口方法和导出能力 | 输入含义及约束、结果、失败条件；适用时说明副作用、幂等、事务或并发限制 |
| 字段、枚举和状态 | 名称不能完整表达的单位、精度、范围、来源、空值语义或状态差异 |
| 非显然业务规则或兼容处理 | 为什么这样处理、保护哪个约束；必要时链接仍有效的协议、缺陷或设计依据 |

业务类和模块的职责说明是本模板对新增代码的明确要求；不能仅以名称可读为由全部省略。公共契约已有继承文档或同一权威定义时可引用，覆盖语义时必须说明差异，不复制同一份长说明。

简单类型别名、显然的私有访问器和局部步骤不机械补注释。不直接修改生成代码来满足注释要求，应检查生成源或配置。公共字段不要求全部逐字翻译名称，但金额单位、时间时区、状态等不可从类型推知的含义必须说明。

## 语言与形式

- 默认使用团队中文，项目明确指定其他语言时遵从项目；标识符与协议字段保持原名。
- 按语言惯例使用原生文档注释：Java 使用 Javadoc，Go 的导出文档以符号名开头，JavaScript/TypeScript 公共能力使用项目采用的 JSDoc/TSDoc，Python 使用项目惯例的 docstring。
- 类型已表达的信息不重复堆砌，参数、返回和异常说明按契约实际需要填写；不套用另一种语言的标签模板。
- 先写职责或契约，再补理解所需的条件。长度以准确为准，不用固定行数截断必要说明；完整设计保留在其权威文档中。

例如 `amount` 的注释应说明“金额，单位为分，非负”，而不是“金额字段”；重试分支说明“下游可能已受理，使用原请求号避免重复扣款”，而不是“失败后重试”。实际单位和行为必须来自项目证据，不能照抄示例当作业务事实。

## 修改与清理

- 调整方法、状态、单位、异常或副作用时同步更新相关注释，不能保留已失效的承诺。
- 删除触及范围内复述代码、逐行翻译、被注释掉的死代码和 Git 变更流水；不加入“本次新增”“修复了”“v2 调整”等过程标签。
- 保留许可证、工具指令、生成标记、公开弃用机制，以及仍有效的法律日期、协议依据和兼容缺陷引用；出现日期或工单号本身不是删除理由。
- 未明确要求批量治理时只处理当前改动范围。批量清理逐条理解，不能用正则全删，也不能误改字符串中的示例、SQL 或协议文本。

## 完成检查

对照本次 diff，核对新增业务职责和公共契约是否有说明，字段单位与状态是否明确，复杂条件是否需要解释原因，已有说明是否仍与实际行为一致。无注释的新增文件也必须进入检查。

语义检查由 Agent 或评审完成。项目已有文档 lint、构建或 CI 时执行适用检查；工具只能证明其覆盖的格式或缺失条件，不能证明业务解释正确，不为宣称合规而新增注释数量指标。
