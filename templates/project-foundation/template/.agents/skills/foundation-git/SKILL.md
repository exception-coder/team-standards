# Git 提交规范

## 提交范围

一个提交对应一个完整、可独立理解和验证的逻辑变更。同一功能所需的前端、接口、数据迁移、测试和文档一起提交；可分别评审和回滚的不同需求或 Bug 分开，不按技术层机械拆碎，也不靠未来未提交文件才能成立。

记录并保护已有工作区与暂存区内容。只暂存本次文件或能可靠分离的片段，核对完整 staged diff；不无差别 `git add -A`，不擅自 stash、reset、取消他人暂存或改写已发布历史。混合片段无法安全分离时保留现场并说明具体阻碍。

## 完成后执行

按项目入口默认约定，在逻辑单元完成、受影响文档同步且适用验证通过后创建本地提交；用户明确不提交或项目要求人工提交时遵守。无改动不创建空提交，验证失败、作业未完成或作者缺失时不以完成名义提交。

读取仓库实际 `git config user.name` 和 `git config user.email`，使用真实作者；缺失时报告，不编造身份或添加 AI 工具署名。提交前证据必须覆盖暂存快照及其依赖，不能用其他未提交修改支撑的通过结果冒充本次通过；同一输入的有效证据无需因提交再重跑。

## 提交说明

标题使用 `type(scope): 具体变化`，scope 可省略，标题不超过 72 字符。type 根据实际选择 feat、fix、refactor、perf、docs、test、style、chore、ci 或 revert。

正文依次使用以下三段中文，写清原问题、关键做法和实际结果，不只列文件、版本与 PASS：

```text
【改动】说明哪个行为或规则怎样改变。
【原因】说明原来在什么条件下有什么问题。
【结果】说明改后表现、已验证范围和仍待验证项。
```

用真实换行写入消息文件，并通过 `git commit -F` 提交，避免 Shell 插值改坏正文。Git 的实际作者身份与正文均须核对，消息文件不依赖任何外部套件脚本。

## 提交之后

核对提交号、实际范围及剩余改动归属。推送、发布和部署分别判断授权，本地提交不自动授权这些操作，不带入来源套件的自动推送白名单。推送失败保留成果，不强推或绕过分支保护。

回滚能力按实际副作用判断；代码可 revert 不代表数据库数据或外部行为可恢复。需要时说明真实恢复边界，不为证明可回滚而执行破坏性操作。
