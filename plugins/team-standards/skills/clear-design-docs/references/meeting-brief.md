# 项目过会模式

用户要求过会方案、方案宣讲或把功能清单与设计汇总给业务和研发讨论时使用。产出可直接讲解的会议视图，不重新制定技术方案，不把普通周报、会议纪要或独立技术评审转成过会材料。

## 从现有材料提炼

读取可取得的页面功能清单及修正说明、业务/页面设计、技术方案和用户已确认的决定；材料缺失时使用已有需求、代码或其他可追溯依据并标明缺口，不为过会强制补齐全套方案。先核对本期范围、系统职责、关键交互及待定事项，区分已有实现、计划新增、已确定与建议。材料冲突时指出影响，不因某份文档较新就将建议当成定论。

过会稿引用这些材料作为依据，不形成第四套独立业务规则。功能编号与来源位置留在备查映射或链接中；页面字段和业务规则用表格逐项确认，正文不铺满编号、技术字段字典、接口路径和大型责任矩阵。原清单和详设中的编号、验收及版本关系继续保留。

## 目录与决策清单

- 按“做什么、怎么做、边界是什么、需要确认什么”组织目录。项目目标与范围、业务流程与分工、核心业务设计、技术与数据、验收交付、待确认事项可作为起点；通常5～7个主要章节、标题不超过三级，仅作阅读建议，按复杂度和用户习惯裁剪，不机械凑数或编号。
- 标题表示独立主题。相近的问题、证据、分工和规则归入同一主题，用简短引导语或表格分组；一段话或一张表能表达的内容不拆成多个标题。字段、指标、异常规则按行审议，不能为压缩目录删除口径、阈值、角色、边界、例外或待定状态。
- 在文末给出按业务块归类的待确认事项索引，区分业务拍板与研发核实，并指向正文对应块；正文对应块保留必要背景、建议和影响。索引只概括问题，不复制一套规则，不另行制造会议决议。
- 总览集中讲指标与统计口径，异常集中讲识别、依据、处理和本场景分工。系统共用职责在整体协作处讲一次，业务块只补本场景特有分工。详细接口、表字段、技术机制和实现约束仍由技术方案承接。

## 按业务大块讲解

开头用简短目标、本期排除项和整体协作图让参会者理解全貌。随后按用户办事流程分成业务大块，每块按以下方式展开：

**对应原型图 → 页面字段与业务规则表 → 业务对象本体与表模型 → draw.io 功能实现逻辑图或时序图 → 本块待拍板问题。**

- **原型图**：从提供的原型、Excel或附件中提取真实页面及必要状态，不用首页代替详情，不伪造缺失页面。旧原型含本期排除项或过时规则时，在相邻位置标明差异，不冒充已修订界面；无对应原型就说明缺口，继续讲清已有依据。
- **对象与表模型**：说清本块有哪些业务对象、它们如何关联、各自保存在哪里。以draw.io对象关系图和简化ER图配合必要的对象—存储映射说明；共享模型集中讲一次，各块只展开关联对象及本次变化。具体深度见下节。
- **实现图**：讲功能怎么完成、系统分别负责什么时用逻辑/流程/泳道图；讲跨系统调用先后、回执、异步结果或版本变更时用时序图。选择适合问题的一种，不要求每块同时画两种。
- **讲解**：用简短中文引出表格，每行只讨论一个字段、动作或规则。保留用户动作、可见结果、双方职责及关键失败行为；接口路径、代码字段、JSON路径、SQL、锁、索引和任务实现留在技术方案，不夹进业务说明。
- **问题点**：紧跟本块图解，写清现有差异、建议或可选方向，以及需要回答的问题。区分会上决定的业务口径和会后由研发核实的能力；文末索引汇总问题并指回业务块，不能用总表取代就地讨论。共用问题集中说明一次并回指。

一个业务大块可跨多张图，按信息密度拆分，不固定页数或板块数。原型与实现图可以同页并排；截图文字或时序标签看不清时改为相邻独立图页，不能无限缩小字号。结尾只需简述开发推进和会后落实方式。

## 页面字段、业务规则与待拍板表

页面内容和业务规则统一用表格表达，便于参会者逐行确认；引导语保持简短，不在表格下面另写一大段隐藏条件。按本块内容选用以下列，不强制合成一张宽表：

| 内容 | 推荐列 | 必须讲清 |
| --- | --- | --- |
| 页面字段与操作 | 页面内容／显示或操作规则／负责方 | 中文名称、必填或选填、取值来源、可编辑范围、点击结果；相关空值、失败和权限提示 |
| 统计指标 | 页面指标／怎么算／点击后看什么 | 统计对象、去重、时间和人员范围、单位、分子分母、零分母；共用范围另列一张短表 |
| 异常或判断规则 | 规则／什么情况命中／阈值与边界／依据来源 | 等于阈值是否命中、适用与排除范围、缺证据怎么显示；数值未定写“待拍板”，不借测试值充当默认值 |
| 系统分工 | 事项／系统甲负责／系统乙负责 | 谁提供事实、谁计算或分析、谁保存和展示；系统名称按实际项目填写 |
| 本块待拍板 | 要定的事／建议或选项／影响的页面或规则 | 明确要回答什么，以及决定后会改变什么；已有决定不重复待定，研发核实项单独标明 |

待拍板表紧跟对应业务块，不把所有问题移到文末。没有实际会议结论时不填“已确定”；不把未答复当成同意。表格过宽时拆成字段、规则、分工等短表，保留全部关键条件，不靠缩小字号或长段落塞入一个单元格。

过会稿讲业务含义，技术方案保存实现合同。比如过会稿写“当前已收到可读文字稿才计入；只有总结不计入”，存储路径与空值校验留在技术方案。精简技术细节不能删掉影响功能的公式、阈值、边界、权限或例外，也不能把这些业务决定推迟为“编码时由AI猜”。对象与表模型图仍按下节保留必要表名、关系和中文用途。

## 业务对象本体与表模型

过会不仅看界面和调用，还要让业务与研发对“对象是什么、关系是什么、数据落在哪里”形成共同理解。至少覆盖本期核心对象及相关存储；不因为精简而省略模型，也不要求每个页面独立建表。

- **业务对象本体**：用中文说明对象含义、稳定身份、关键属性、主要状态及生命周期。关系标明业务含义、方向、基数和必要的可选性；版本、历史、自关联或带属性的关系需单独表达，不能用一个模糊箭头代替。
- **表模型**：给出已核实的表名及中文含义、所属系统、主键、关联字段、关键状态/时间/版本字段，以及影响理解的唯一约束。图中明确一对多、多对多及中间对象，区分逻辑关联与实际数据库外键。字段保留必要类型和中文说明，完整数据字典、索引及DDL回链数据库设计。
- **本体到存储的对应**：说明对象映射一张或多张表、共享表中的哪部分、JSON快照或文件；计算指标注明计算来源，不虚构结果表。一个对象不必等于一张表；跨系统同名或同ID不代表同一对象，需说明来源身份和映射关系。
- **权威来源与本次增量**：标明哪个系统维护事实、其他系统保存的是引用还是副本/投影；区分已有复用、计划新增/调整和待核实，说明关键读写与页面操作如何对应。未知表名、PK/FK或类型不能画成既有事实。
- **模型问题就地讨论**：如对象边界、客户去重、版本历史、状态含义、数据归属和跨系统关联是否一致，放在对应模型图或业务块下。明确问题影响哪个功能，不把全部表字段变成审批清单。

复用已核对的本体与数据库设计；缺少业务模型时按需用[业务本体建模](../../business-ontology-modeling/SKILL.md)补对象语义，涉及库表决策用[库表设计](../../database-design/SKILL.md)。既有表结构通过[后端证据](../../backend-evidence/SKILL.md)核对元数据、DDL/迁移或读写映射；仅有代码证据时注明覆盖，不宣称运行库已验证。过会汇总不自动授权数据库写入或迁移。

简单模型可在一张图中分开业务对象和存储映射，复杂模型拆成“对象关系”和“表关系”两张图；图中明确视图层次，不能把概念对象当成物理表。纯交互块若不改变数据模型，引用共用模型即可。

对象关系图优先展示中文对象与关系；逻辑ER只保留表名、主键、关键关联字段和必要状态，采用标准基数符号。业务规则、数据来源与待确认事项放在图旁表格，不塞进实体框；详细字段和物理约束回链技术方案。具体画法见[ER分层与关系标记](../../architecture-diagram-design/references/er-design.md)。

## draw.io 与输出

绘制复用[架构图技能](../../architecture-diagram-design/SKILL.md)的原生模板、布局和轻量验收。默认交付可编辑 `.drawio` 及同源预览，保留原生节点、文字、连线；截图可嵌入作对照，不把整张实现逻辑栅格化后冒充可编辑。

已有正确的架构源图优先复用，仅调整本次需要的视图。图上标明当前实现、目标设计或待确认，调用箭头与系统责任一致；未知能力不能靠画图补成事实。目录、格式和载体沿用用户及项目约定，不默认另做PPT、网页或发布到外部平台。

从最终源图导出并逐页检查中文、截图可辨认程度、标签、遮挡和箭头，抽查文字、节点和连线可编辑；源图修改后重导出对应预览。只有XML结构检查时如实说明未渲染，不用自制近似预览冒充draw.io导出。

## 范围保持与会后回写

缺少对应材料时指出具体缺口，不编造原型、角色授权、已实现能力、工期或会议决议。已确定事项不重新要求审批，待定项未答复不视为同意，也不自动冻结其他可推进的部分。

没有实际会议结论时只标讨论稿；会后收到结论且用户要求同步时，范围回写功能清单，交互回写业务设计，实现约定回写技术方案。各块记录“决定了什么、谁落实、何时补齐”，负责人和时间未知就保持待定，不另建重复决策流程。

## 完成检查

- 首次参会者能沿图讲明目标、系统分工、当前要开发的功能和主要交互。
- 每个业务块有对应原型或明确缺口、涉及的对象本体/表模型或共用模型引用，以及适合该块的逻辑图/时序图；问题放在该块下面。
- 对象、关键状态、关系基数、存储映射、数据归属和本次模型变化能对应；逻辑关系不冒充实际外键，未知结构不冒充已存在。
- 精简编号没有丢掉本期范围、排除项、关键例外和原材料的可追溯关系。
- 页面字段、指标和业务规则可逐行审议，待拍板问题位于对应块下；正文没有混入代码字段或实现过程。技术方案、设计方案和功能清单的共同规则一致，既有外部发布是否同步按用户授权处理。
- 链接可达，源图与预览一致；建议、事实、未知和交付状态没有混淆。
