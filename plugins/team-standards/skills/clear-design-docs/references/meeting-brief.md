# 项目过会模式

把已有需求和设计提炼成参会人能快速理解并作出决定的图解主稿。复用[统一图文准则](../../markdown-writing-standards/SKILL.md#图解主稿与按需详查)和[过会模板](../assets/meeting-brief.md)，不把详设逐章搬入会议。

## 从现有材料提炼

先核对目标、已确认范围、关键流程、当前实现和待定事项；来源可以是功能清单、业务设计、技术方案及用户确认。缺少全套材料不阻止编写，缺口就地标明。过会稿引用唯一正文，不形成另一套规则，也不自动实施方案或把未答复视为批准。

围绕“问题是什么 → 整体怎么做 → 关键路径 → 难点与取舍 → 验收和需要决定什么”安排讲解。简单问题可合并，复杂问题可拆成相邻图页；不固定章节、页数或每块图表数量。

## 一页讲清一个结论

- 标题写判断或预期结果，例如“批次提交后才计进度，失败从断点恢复”；“运行机制”这类主题词本身不是结论。
- 用一张主图展示边界、参与方、关系或先后顺序。图下通常只补少量条件、理由、风险或待定事项；图能讲清的不再写一遍。独立阅读时关键条件仍可定位。
- 每个难点写清触发条件、采用的办法及代价；存在实际可行替代时再比较选项。不要把实现步骤、参数数量或图多当作方案充分性的证明。
- 影响决策的业务范围、权限、统计口径、阈值和失败后果必须可见。完整字段字典、SQL、内部版本标识和方法代码放在详设或接入指南。

## 按问题选择图

| 会上要理解的问题 | 优先采用 | 详设承接 |
|---|---|---|
| 整体如何协作、谁负责什么 | 全景图或系统边界图 | 包、类、接口清单 |
| 用户怎么配置或操作 | 对应原型、配置示意或短流程图 | 完整字段表、所有交互状态 |
| 数据和对象如何关联 | 核心对象关系或简化 ER | 物理字段、索引、DDL |
| 跨系统如何执行、失败怎么恢复 | 流程、泳道或时序图中适合的一种 | 完整协议、重试参数和少见分支 |
| 为什么选这个办法 | 候选方案对照图或简短比较表 | 详细测量和验证证据 |

不要求每个业务块都具备“原型＋字段表＋对象图＋ER＋时序图”。共享模型只讲一次；数据归属或关系本身影响决策时展开，不相关时链接已有模型。

原型缺失可画明确标注的交互示意，不能冒充已上线页面；旧原型与本期范围不同则就地说明。当前实现、计划新增和待核实分清。

## 业务对象本体与表模型

这个视图用于解释身份、关系、状态或数据所有权上的重要决定。先用中文讲对象，再按需要展示所属系统、基数、关键标识及实际存储位置。关系不能含糊，未知表名、PK/FK或约束不画成既有事实，逻辑关联不冒充物理外键。

完整物理模型保留在数据库设计；过会只展示当前问题所需的一部分并提供入口。需要作出模型决策时复用[业务本体建模](../../business-ontology-modeling/SKILL.md)和[库表设计](../../database-design/SKILL.md)，不因汇总过会材料启动无关全库审计。

## 问题与验收就地说明

本块有实际待决事项时，在图旁说明“要决定什么、建议及代价”。业务拍板与研发核实分开；技术事实不能通过投票替代验证。无待定项时不凑问题。

结尾保留简短验收场景和未决事项索引，已有编号留在备查映射中，不铺满标题和正文。只有实际收到结论，才记录决定、责任人和时间并回写唯一设计来源。

## draw.io 与输出

新绘或改绘图默认用[架构图技能](../../architecture-diagram-design/SKILL.md)交付原生可编辑 `.drawio` 与同源预览，保留节点、文字和连线。项目目录与用户指定格式优先。正文就地显图；PPT 式写法不等于必须再生成 PPT 文件。

从最终源图导出，检查中文、字号、连线、裁切和实际阅读宽度。图拥挤时拆图或减少非关键细节，不无限缩小字号。发布到飞书核实项目及二级目录，并读回正文、图片和源图入口；抽查说明范围。

## 完成检查

- 首次参会者能沿图说明目标、分工、主路径、设计难点和待定事项。
- 主稿与详设的规则和状态一致；关键条件、风险与失败结果没有因压缩丢失。
- 每张图回答明确问题，文字补充图未表达的内容；完整契约和接入示例可按需找到。
- 已确认、建议、待核实和实际完成状态分清；无虚构原型、会议决议或验证结果。

方法依据与研究边界统一见[图文准则](../../markdown-writing-standards/SKILL.md#图解主稿与按需详查)。
