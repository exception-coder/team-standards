# 清晰实用的概设与详设

目标：同事在会议上能讲清设计思路，开发者和 AI 能据此实施基础版；不把设计文档写成组件清单、字段堆积或扩展框架说明书。

## 先确定本次工作边界

- 用户要方案先审查时，只提交优化方案；要评审时给出定位明确的问题和建议；授权改文档时原位修改。使用本技能不代表授权编码、换技术栈或部署。
- 先读项目规则、文档索引与相关设计。遵循现有设计绑定及治理流程，区分拟建、实现、验证和发布状态，不把新写的设计描述成已实现。
- 保留已确认的技术选型和范围，只调整本次相关章节。存在问题时提出依据，不借“最佳实践”全面重写。
- 文档位置、绑定、固定章节及兼容方式遵循 [设计内容契约](../change-readiness/references/design-output-contract.md) 和项目已接受约定；保留已有同文件双章节，不另设一套模板。总览维护跨域共识，领域设计引用它，不复制全局规则。

## 建设哲学：先完整的基础版，再按需求扩展

- 首期覆盖常见必备场景，采用明确默认方案；成熟协议、密码学和基础 SDK 优先复用，平台业务规则与管理体验可自主实现。
- 基础架构阶段不强制等待真实客户、业务单据或报表接入。用明确标注的标准样例验证可用性；真实环境的字段、协议和业务口径仍须在接入时核验。
- 不因“业内常用”强制增加缓存、独立身份服务、网关平台或微服务；不把 AI 编码速度视为可靠性证据。
- 在确有变化的边界留接口，首期提供一种默认实现；不为想象中的需求建设插件市场、双引擎并存或通用编排框架。
- 后置能力可以简述方向，但不进入首期建表、接口实现、配置页面和验收清单。若已有代码或已接受契约，不能仅通过改文档删除其义务。
- 简化能力范围，不简化正确性。事务、幂等、并发、访问控制、审计和失败恢复按所选能力的实际风险覆盖。

每个领域说清四项：**基础版能力、默认实现、扩展位置、后置能力**。可以合成一张表，不要求为四项各建章节。未确认事项只标注影响范围及后续确认安排，不把不影响基础开发的事项变成阻塞条件。

## 概设讲取舍，详设讲如何落地

| 文档层次 | 读者应能回答 | 内容深度 |
|---|---|---|
| 概设 | 解决什么问题、为何这样划分、谁拥有数据、如何协作、首期交付什么 | 关键概念、边界、核心对象关系、主要流程和设计取舍；避免物理字段堆积 |
| 详设 | 对象怎样关联、规则怎样执行、失败怎样处理、怎样验收 | 用业务语言说明对象、字段含义、处理步骤、约束和异常；保留实施所需的准确标识与规则，只细化本次确认的交付范围 |
| 技术方案 | 用什么技术、怎样实现和部署 | 组件选型、协议、代码结构、数据库实现、缓存与并发机制、运行配置；概设和详设按需引用 |

本技能负责表达质量，不覆盖团队设计内容契约的固定章节与适用项目的治理要求。按影响补齐相关内容，不强迫历史文档整篇改版；不适用项按内容契约解释原因，不用空标题凑模板。技术实现可在详设的功能技术实现及共享章节中维护；项目明确要求独立技术方案时引用唯一正文，不重复抄写。

## 用词：业务含义先于技术名称

- 概设和详设都面向会议讨论与跨岗位协作，不能把“详设”理解为可以堆技术词。标题、图中标签和段落首句先说具体的人、资料、动作与结果；英文对象名放在括号或字段表中，供开发对应。
- 避免用“治理辅助对象”“权威事实”“有效性屏障”等抽象词代替解释。例如写“人员资料的来源、核对与紧急停用”“人员状态以哪个系统为准”。术语确有必要时，首次出现就解释其含义。
- 分清相邻概念并说明实际影响：人员是否可用、登录是否有效、有哪些操作权限分别回答不同问题；涉及停用或冲突拒绝时，明确谁会被阻止、什么时候恢复，不能笼统称为“权限限制”。
- 技术方案已有的实现细节通过链接引用，概设和详设保留理解业务规则所必需的约束。通俗化不改变字段标识、状态含义、判定顺序、安全要求和责任归属，也不把关键规则全部移到技术方案。
- **逐段试讲**：按目标听众的理解方式，审读本次范围内的每个段落、表格和图，不只检查标题或搜索术语。读者应能说明“谁做什么、为什么需要、何时生效、失败怎么办”；只检查与该段相关的问题，不要求每段套齐模板。若必须猜指代、跨多处拼规则或先解释一串术语，原位改写。
- **替换前核对含义**：对照原文检查适用对象、成功承诺、生效时点、失败行为与安全边界。不能把人员和服务账号缩成“登录人”，把可重试说成“一定成功”，或把下一次请求生效说成无条件即时生效。保留必要术语并就地解释，比失真的口语替换更好。
- 外部评审建议逐项选择“采纳、改写后采纳、保留原意”，以当前已确认设计为准；不因建议标注“只改表达”就假定语义不变。交付说明关键取舍，不必另建一份对照文档。典型误改见 [术语替换反例](references/examples.md#术语替换先核对含义)。
- 范围内的存量说明与新写内容一起检查，不机械替换全仓术语；相同词在不同模块或接口中可能有不同含义。

## 写作：先给读者路径，再给细节

- 每节开头用一句话说明要回答的问题。先用业务语言解释概念，再给英文对象名、状态码或接口名。
- 一个段落说明一个问题。先讲正常路径，把例外集中到相邻的异常表；避免同段交织状态转换、来源选择、缓存延迟和安全策略。
- 多对象比较用表；有先后次序的判定用编号步骤；条件与结果用决策表。每个分支说明结果和下一动作，避免反复写“按策略处理”却找不到策略定义。
- 复杂状态章节可按“状态含义与转换 → 判定顺序与取值来源 → 异常处理”组织。状态、判定结果和失败原因分开，例如人员状态与资料过期不是同一维度。
- 每个复杂模型给一个短样例，解释对象为何存在，例如换岗为何新增任职而不覆盖历史。样例不自动升级为全局业务规则。
- 保留必要边界，但集中表述一次；避免重复的“不做什么”“待评审”“须确认”。简洁以减少理解负担为准，不以字数最少为目标。

重写长段落或补对象图时，可读取 [references/examples.md](references/examples.md) 中的示例。

## 对外接口：字段必须有中文说明

- 输入、输出和事件字段均使用“`英文名`（中文含义）”，字段较多时单列字段说明表；接口名或字段名本身不能代替说明。相同名称在不同接口中含义不同，按当前上下文解释，例如任务定义 ID 与审批待办 ID。
- JSON 示例保持合法 JSON，不加入注释；在相邻表格解释每个字段，包括嵌套字段。枚举值、状态和错误码说明中文含义及必要的处理动作，不能只列英文码。
- 影响调用理解的必填性、默认值、单位、时间含义和版本用途，按已有设计说明；未确定的内容明确标记待细化，不猜测字段、类型或新增接口义务。已有中文描述而尚未确定英文名称时，保留中文，不为凑表虚构名称。
- 逐个接口核对字段解释与示例，不用一张脱离上下文的全局词汇表代替；实现细节仍按需引用技术方案。

## 关系复杂就配图，图与文字分工

当对象有多对多、中间关系实体、自关联、多来源映射，或读者难以从字段表理解关系时，补**逻辑 ER 图**。字段表、数据流向图不能替代它。简单单对象说明不强制配图。

- 先解释“对象为什么分开”，再给关系图、必要字段和约束；已有文档可把图放在字段表之前。
- ER 图标出对象、关联字段和基数，解释一对多、可选关系、当前与历史记录的差别。优先采用中文显示名或中文注释，保留与模型一致的英文标识。
- 区分本领域对象与外部参照、逻辑关联与物理外键。未确认的基数或字段明确标为待定，不为画图虚构实体、外键和约束。
- 人员、任职等主要对象与资料来源、核对记录、变更记录分图表达。说明这些记录如何协作时可用流程图，并说明连线不代表一对一或一对多关系。
- 按问题选图：对象关联用 ER 图，调用及事务顺序用时序图，状态迁移用状态图，归属和依赖用结构图。已有合适的图就复用，不为每节凑图。
- 图只放关键字段和连线；文字解释设计理由，表格承接详细约束。避免一张图展示全部实体、字段和异常。
- 用项目支持的 Mermaid 等格式；遵循 [Markdown 与 Mermaid 格式规范](../markdown-writing-standards/references/markdown-format.md)。校验语法并尽可能实际渲染、检查标签和连线是否可读。渲染未完成时如实说明，不把静态检查称为渲染通过。

## 完成前的针对性评审

1. **范围一致**：总览、概设、详设模型、接口、默认配置、实施任务和验收是否把同一能力标为首期？后置能力是否混入首期验收？只更新受影响载体。
2. **语义一致**：图的基数与字段约束是否一致？默认方案与“待定”是否矛盾？状态、版本、事实拥有者及来源是否前后一致？
3. **可理解与准确**：完成范围内的逐段试讲；读者能否解释核心对象、关系和关键流程？每项术语替换是否保持对象范围、承诺、生效时点与失败规则？不能以“已经补注释”代替这项内容审读。
4. **可实施与可验收**：默认实现是否具体？普通成功、关键失败及恢复是否可用样例验证？安全和数据正确性有没有被删成“后续完善”？
5. **维护成本**：是否为了扩展引入未用表、抽象层、组件或管理界面？能否只保留模块边界与接口？
6. **真实验证**：检查受影响标题、链接、表格、围栏和图表。纯文档改动不跑无关运行时测试；行为或接口契约变更按项目治理流程处理。

格式检查与内容审读分别报告：链接、表格、图表通过只证明结构或渲染正确，不证明全部设计清楚、准确；未审读范围不能宣称已全面优化。

结构、状态与具名审阅沿用 [设计内容契约](../change-readiness/references/design-output-contract.md)，不另加一轮审批。机器校验不能证明逐段试讲完成或代替人工认可。

交付简述改了什么、为什么更易理解、完成哪些检查及剩余未验证项。提交遵循项目要求；个人技能等仓外资产说明实际保存位置，不虚构 Git 提交。
