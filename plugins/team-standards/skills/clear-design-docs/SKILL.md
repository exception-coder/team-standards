# 设计文档编写与评审

目标：业务同事能讲清设计，开发者能据此实现并验收当前范围。共同准则见[工程宪法](../change-readiness/references/engineering-principles.md)，通用措辞归[人话](../plain-writing/SKILL.md)。

## 按请求选择模式

- **编写或精简**：使用下方设计表达规则，维护当前范围的模型、接口和验收；不自动实施设计中的功能。
- **项目过会或方案宣讲**：读取[过会模式](references/meeting-brief.md)，从功能清单、业务设计和技术方案提炼会议视图；按业务大块展示原型图、对象本体与表模型、draw.io逻辑图/时序图，简短讲解后就地列问题。正文不堆编号和详细接口表；原清单与详设保留编号及验收，以下完整详设结构不机械套入过会稿。
- **独立评审**：读取 [评审模式](references/review-mode.md)，默认只读，给出有证据的最小修正建议。没有编写授权时不补章节、不重画图、不创建另一份设计。
- 编写中的自检复用同一份事实与核对结果；仅表达问题不再启动一轮独立实质评审。已有评审证据覆盖当前输入时直接沿用。
- 需要作出库表或技术实现决策时，按[工程设计输出规则](../change-readiness/references/engineering-design-output.md)选专项设计入口；在既有方案上做清晰表达时直接使用本 Skill。

## 编写与精简判断准则

- 概设解释价值、范围、边界、核心对象和协作；详设明确规则、字段含义、处理顺序、异常与验收。技术实现维护唯一正文，按需引用。
- 本期能力、默认实现、扩展边界与后置方向清楚即可；尚未确定方案才用[悟道](../architecture-reasoning/SKILL.md)，已定方案不重开取舍。
- 每段让读者能说明相关的人、资料、动作、条件与结果。条件复杂时用决策表，关系复杂时配图；术语保留准确标识并就地解释。
- 正式方案先给结论与[全景图](../change-readiness/references/engineering-design-output.md#全景图与正文)，优先交付可编辑 draw.io。正文补图上未展开的规则、取舍与验收，共用内容引用唯一正文。
- 按本次范围逐段核对语义，包括对象、承诺、生效时点、责任与失败行为；外部建议也需核对，不能因标注“只改表达”就直接接受。

## 必要约束

- 章节、功能编号和生命周期沿用[设计内容契约](../change-readiness/references/design-output-contract.md)及项目约定，保留已有的同文件双章节绑定。后置能力单独记录，规划、实现、验证和上线状态分清。
- 输入、输出和事件字段有中文含义；嵌套字段、枚举、错误码及影响调用的必填性、默认值、单位、时间性质和版本用途逐接口说明。JSON 示例保持合法，未知类型或字段标待定。
- 多对多、中间实体、自关联或多来源映射等复杂关系配逻辑 ER。逻辑对象与物理表分清；一个图内一个对象一个框，层级用自关联，关联连全两端，条件目标写清互斥及选择条件。
- ER 框内保留标识、关联及影响理解的类型/状态/有效期字段和中文含义，连线对应实际字段与基数；完整字段表承接细节。未知 PK/FK、类型和约束不虚构，逻辑关联不冒充物理外键。
- 复杂模型可分图，但名称、范围及对象覆盖一致；图拥挤时调整或拆分，不能删光关键字段。按项目支持格式实际检查可读性，未渲染说明缺口。

## 精炼反例

- 把“下一次请求生效”改成“立即生效”：简短却改变了承诺。
- ER 中另画“父菜单表”：同一菜单对象应使用自关联。
- 接口只有英文 JSON：补相邻中文字段表，未知参数留待确认。
- 把实现完成写成已经上线：保留真实交付阶段。

## 按需参考与完成边界

长段改写、对象图及语义误改见[示例](references/examples.md)。格式见[Markdown 规范](../markdown-writing-standards/SKILL.md)，独立实质评审用[设计评审](references/review-mode.md)，不再制造另一份问题清单。

完成时受影响的范围、模型、接口与验收一致，业务读者可理解，开发所需条件可定位。内容审读与结构/渲染检查分别说明；基础样例可以验证设计表达，不能替代真实系统接入证据。
