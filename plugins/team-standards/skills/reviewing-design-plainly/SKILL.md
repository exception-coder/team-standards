# 务实的设计文档评审

评审帮助团队决定当前方案能否支撑**本期**开发与验收。优先指出会导致做错、做不成、无法验收或明显增加维护成本的问题；不要为了展示评审深度扩写系统。结论用业务人员也能理解的话说清楚，必要技术名词就地解释。

## 先确定评审依据

1. 读取目标文档的当前版本、项目入口、已接受的需求/规格和直接引用；仓库内文件核对工作区状态，避免拿旧提交评当前稿。仅在结论依赖实现事实时，定向查代码、配置、表结构或运行证据。
2. 从现有资料确定本期范围、用户与业务目标、部署/数据边界和已确认约束。未写明的前提先作为待核实假设；只有它会改变关键结论或阻塞实施时才提问，不把评审变成开场问卷。
3. 区分文档原文、项目事实、行业参考和自己的推断。引用能定位到文件章节或行；资料不足时写明“待核实”，不能把推测说成既有故障或确定需求。

## 按风险审查，不按清单凑问题

- **目标与范围**：概设、详设、技术方案、任务和验收对本期能力及交付状态是否一致？目标设计有没有冒充已实现或已上线？
- **业务闭环**：主要角色、正常流程、必要异常、权限与数据范围是否能串成可执行结果？遗漏会不会让本期功能做错或无法验收？
- **模型与规则**：对象、状态、字段、关系图、接口及数据来源是否互相支持？同一规则是否出现冲突、未定义的判定顺序或无法保持的数据约束？
- **实现与运行**：已选技术和现有系统是否相容？关键失败、重复执行、并发冲突、恢复及基本安全控制是否按真实风险处理？能否用明确场景验证结论？
- **复杂度**：新增表、抽象层、组件、配置项和跨服务流程是否服务本期问题？有更简单的现有能力可复用时，建议收窄而非重建。

这些是发现问题的视角，不要求每篇文档逐项打勾或补齐所有图表。概设重点核对业务价值、范围与边界；详设重点核对规则和可验收性；技术方案重点核对实现路径、依赖与运行风险。表达是否清楚、关系图是否准确，复用 [clear-design-docs](../clear-design-docs/SKILL.md) 的对应规则；固定目录、状态与绑定仍归 [设计内容契约](../change-readiness/references/design-output-contract.md)。

## 把未来风险放在正确位置

- 本期没有高流量、高并发、大数据量目标或证据时，不强制缓存、分库分表、微服务、双写、消息队列或压测指标。可以提示将来何时需重新评估，并保留清晰的数据归属和替换边界；“可切换”不等于首期同时实现两套方案。
- 冷门业务场景默认列为提醒或待观察。只有它已在本期范围内、属于安全/数据正确性底线，或一旦遗漏就会造成不可接受损失时，才提升为必须处理。
- 表结构满足已知业务关系、标识和约束，并为合理演进留空间即可；不为想象中的字段、状态和租户模式预建通用模型。留空间不能代替本期必要的数据约束、索引或迁移说明。
- 性能、可用性和安全使用与项目风险相称的基线。行业质量模型可帮助发现遗漏，但不是要求实现其全部特性的验收清单。已承诺的 SLA、监管义务或明确容量目标仍必须按实际合同审查。

需要行业对照时，核对当前版本和适用范围，仅引用能改变本次判断的条款。[arc42](https://arc42.org/overview/) 提供可裁剪的架构表达视角，[ISO/IEC 25010](https://www.iso.org/standard/78176.html) 提供产品质量特性参考，[OWASP ASVS](https://owasp.org/projects/asvs) 提供 Web 安全验证要求；三者都不自动成为本项目的完整验收清单。

## 输出可执行的评审结论

先给一句总体判断，再按影响排序列**实际发现**。每条包含：位置或证据、问题与当前后果、最小修正建议，以及“已核实 / 待核实”。不要列没有问题的角度，也不要用字段齐全或机器 PASS 宣称内容正确。

将发现区分为：

- **必须修正**：与已接受事实矛盾，或本期主要流程、权限、数据正确性、基本安全、可实施/可验收性存在实质缺口。
- **需要决策**：存在两种合理解释且会改变本期实现；给出推荐选项和不决策的实际影响。只把真正不能自行消除的业务选择交给用户。
- **提醒**：未来规模、罕见场景、表达改进或低成本演进点；说明触发再评估的条件，不列为当前通过门槛。

问题少时用简短列表；决策多时可以用“已确定 / 待决定”两表，但不强制空表或冗长列。没有实质问题时直接说明“在已审范围内未发现需修改的问题”，并交代核对过的范围和未取得的证据。评审意见不是自动阻断 Hook，也不等于人工业务批准。

独立评审默认只读。用户同时要求修改文档，或已有明确实施授权时，可按最小建议原位修改并核对受影响引用；不因本 Skill 再要求一次许可。源码实施、上线及 OpenSpec 生命周期仍由对应流程处理。
