# 每日工作日志

## 何时记录

- 各档作业默认由真实 Git 提交和验证记录承载历史，不因改动规模自动写日报。
- 用户要求汇总时按指定作者、日期和项目读取 Git 历史，区分已提交与未提交结果；默认直接回答，不额外落盘。明确要求持久记录或项目明确约定日报时才执行下面的写入流程。
- 用户要求记录时立即写入；要求查询时只读。纯文档、配置变更不自动触发；team-standards 决策型变更由 dev-log 负责，普通措辞修改不补造决策日志。

## 写入与合并

1. 默认使用 `{USER_DOCUMENTS}/ai-docs/{project}/work-log/{YYYY-MM-DD}.md`；project 取业务项目目录名，日期和时间使用本地时间。系统无 Documents 目录时使用 `~/ai-docs/`。首次写入说明实际路径，不自动迁移历史日志。
2. 先读当天文件，以用户指定主题、Bug 问题或需求主题匹配已有条目；同主题多轮修改合并，新增结果去重，不能每轮重算或重复追加。没有文件且需要记录时才创建。
3. 沿用已有格式；新文件使用“Bug 修复”和“功能开发”分区，条目编号 B1/F1 按日递增。重构和迁移归功能并在标题注明，混合任务按主诉归类。
4. 每条只写完成结果、关键验证及必要的已有文档链接；不抄完整文件清单、提交正文、AI 对话或失败尝试。不为日志新建 Bug/设计报告，也不填写无意义的“关联文档：无”。
5. 工时默认不填；用户或项目需要时优先使用实际提供或可靠记录的时间，估算明确标为估算。按主题整体更新，不按文件数、文档数或对话轮次机械累加，不把估算当实际工时。
6. 写后核对主题、重复项、路径和事实，交付时简述已更新即可；查询不存在的日志时如实说明，不创建空文件。

## 路径与边界

个人日志默认不入项目仓库。用户明确指定项目内路径或要求上传时遵从，并按 [文档生命周期规则](../markdown-writing-standards/references/document-index-workflow.md) 检查唯一归属、必要链接和 Git 忽略状态；不擅自解除忽略或迁移、删除历史文件。只记录实际完成的工作，不能为“完整日报”补造结果。
