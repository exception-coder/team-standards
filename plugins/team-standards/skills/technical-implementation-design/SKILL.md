# 技术实现设计

把已确认的需求落到现有系统的职责、契约和调用链，让接手人能从具体入口开始实现和验证。按[工程设计输出规则](../change-readiness/references/engineering-design-output.md)裁剪深度。

## 从现有能力到目标实现

- 按[实施定位](../change-readiness/references/code-orientation.md)核对模块、包、入口、调用方、公共组件或 Starter，以及既有接口、权限和测试。区分已有路径、拟复用能力、目标变化和待证实假设。沿用项目架构，新增职责或依赖写明原因。涉及分层时参考 [DDD-lite](../architecture-ddd-lite-fullstack/SKILL.md)。
- 新增服务、通用框架或异步链路要对应当前业务和必要保证，先核对现有能力能否满足；推测中的扩展后置。保证清晰职责及可测试性，失败恢复等确有需要的能力不能为了少组件而省略。
- 概设使用[概念设计模板](assets/conceptual-design.md)。说清本期目标、系统边界、默认实现、核心链路、主要影响和关键取舍。图用于讲清模块或系统协作，复杂条件和异步顺序再补流程或时序。
- 详设使用[详细设计模板](assets/detailed-design.md)。给出受影响的模块/包及职责、接口或事件契约、执行顺序、状态转换、数据读写和异常结果。接口字段说明业务含义、类型、必填、校验及错误行为。明确会受影响的现有调用者和兼容策略。
- 按风险展开权限与数据范围、事务边界、幂等与并发、重试与恢复。涉及异步或跨系统写入时，说明提交、消息可见、重复执行及部分失败后的状态和责任。涉及配置或发布时，写默认值和生效条件、发布顺序、观测与恢复。局部方案只保留受影响部分。

## 交付自检

- 能从一个实际入口走到可观察结果，定位实现点和关键依赖。验证按影响覆盖成功、关键失败、权限/数据范围、重复执行及旧调用者，明确条件、预期结果和证据来源。
- 有结构变更时引用[库表设计](../database-design/SKILL.md)中的约束、迁移及兼容窗口，在这里说明应用如何配合读写和发布，保持边界与验收一致。
