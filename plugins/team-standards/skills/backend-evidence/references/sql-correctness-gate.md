# SQL 正确性门禁

## 目标

防止 AI 生成的 SQL 在语法、名称解析、Schema、动态分支、结果映射或发布制品环节出现可机械发现的错误。正确性门禁与查询性能门禁分开：前者回答“能否按契约正确运行”，后者回答“在目标数据规模下是否可接受”。

---

## 证据与归属

| 证据 | 负责回答 | 归属 |
|---|---|---|
| 项目 DDL、迁移脚本、测试库元数据 | 表、列、类型、约束是否真实存在 | 目标项目 |
| Graphify 与源码 | Mapper、调用链、结果对象和当前实现位置 | 可再生事实层 |
| OpenSpec `specs/` 与活动 `changes/` | 已接受行为契约与本次准备改变的行为 | 目标项目 |
| 团队 SQL 规则 | 跨项目稳定的正确性底线 | `team-standards` |
| Mapper 集成测试与目标数据库解析 | 最终动态 SQL 是否可运行、映射是否正确 | 目标项目 CI |

不得把 Graphify 推断当成 Schema 真相，也不得用 OpenSpec 的期望行为证明当前 SQL 已正确实现。项目特定数据库版本、方言、DDL、Mapper 分支和测试数据必须留在项目自身。

---

## 编写约束

### SQL-C01 多数据源查询全限定

一个查询块只要引用两个或更多表、视图、CTE 或派生表，`SELECT`、`JOIN ON`、`WHERE`、`GROUP BY`、`HAVING` 和 `ORDER BY` 中的实体字段必须使用表别名限定。

```sql
SELECT
    m.id,
    m.develop_id,
    latest.latest_date
FROM milestone AS m
JOIN latest_milestone AS latest
    ON latest.develop_id = m.develop_id
WHERE m.status = 1
ORDER BY m.id;
```

不要只限定当前已经重复的字段。后续表结构新增同名列时，未限定字段也会从可执行变成歧义。

### SQL-C02 禁止多数据源通配投影

多数据源查询禁止 `SELECT *`、`table.*` 和派生表透传 `*`。必须显式列出输出字段，结果标签必须唯一、稳定，并与 Mapper 或 DTO 映射一致。

### SQL-C03 派生表声明输出契约

CTE、子查询和派生表必须显式声明输出列；外层继续使用派生表别名限定。重复业务字段需要用明确结果别名区分，不得依赖驱动对重复列名的隐式处理。

### SQL-C04 不得猜测 Schema

写 SQL 前读取项目当前 DDL、迁移脚本或可信测试库结构。DDL 缺失或版本不明时，明确标记“Schema 未验证”，不得凭字段命名习惯臆造表、列、默认值、索引或约束。

### SQL-C05 动态 SQL 覆盖有效分支

MyBatis、iBatis 或其它模板 SQL 至少验证会改变 SQL 结构的分支：空值与非空值、单值与集合、每个条件分支、可选 JOIN、分页、排序和聚合组合。只检查 XML 原文不能视为完成验证。

### SQL-C06 结果映射显式稳定

查询结果必须校验列标签、类型、空值和一对多行数语义。存在同名来源列、聚合列或表达式时显式写 `AS`，不得依赖字段顺序或静默覆盖。

### SQL-C07 参数化与方言一致

数据值使用绑定参数；数据库标识符不能通过不可信输入拼接。验证环境必须与目标数据库产品、主版本和关键兼容配置一致，不得用 H2 等近似方言证明 MySQL 或 Oracle SQL 正确。

## 分层验证

| 层级 | 方法 | 处理 |
|---|---|---|
| 编辑期快速反馈 | Hook 或 SQL AST/Lint 检查多表裸字段、通配投影、未知别名等 | 启发式只告警；完整解析后的高置信度错误可阻断 |
| Schema 校验 | 对照项目 DDL、迁移脚本或测试库元数据 | 缺失时阻断“已验证”结论 |
| 数据库原生校验 | 在匹配版本的临时或测试数据库执行 `EXPLAIN`、预编译或安全查询 | 解析、名称解析或方言错误阻断 CI |
| Mapper 契约测试 | 通过真实 Mapper 参数生成最终 SQL，覆盖动态分支并验证结果映射 | 失败阻断 CI |
| 查询性能验证 | 按 `query-performance-gate.md` 获取计划、行数和计时证据 | 高风险且证据不足时不得宣称生产可用 |
| 发布制品校验 | 干净工作区构建一次，记录 Git SHA，测试与部署复用同一制品 | SHA 不一致或复用旧输出时阻断发布 |

通用 Hook 不连接项目数据库，也不扫描整个仓库；真实数据库验证必须由项目 CI 提供。建议项目暴露单一命令，例如 `mvn clean verify -Psql-contract`，内部负责应用 DDL、启动匹配数据库、执行 Mapper 契约测试并汇总全部失败。

## 发布缓存边界

- 可以缓存 Maven 依赖仓库，不缓存项目 `target/` 等编译输出。
- 测试和部署必须消费同一次构建得到的不可变制品，不在部署阶段重新打包。
- 制品写入 Git SHA；部署后校验“期望 SHA、制品 SHA、运行实例 SHA”一致。
- 首个 DDL 或 SQL 错误不得终止后续独立用例的收集；Schema 建立成功后，应验证全部变更 SQL 并汇总问题，避免前序错误长期掩盖后续错误。

---

## 事件回写

重复出现的 SQL 正确性缺陷应记录为项目技术陷阱候选，至少包含错误类型、触发 SQL、遗漏门禁、补充测试和适用数据库版本。只有跨项目稳定复现的规则才提升到团队标准；单个项目的表结构、Mapper 写法和发布命令留在项目内。
