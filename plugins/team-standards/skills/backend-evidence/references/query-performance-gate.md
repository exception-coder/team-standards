# 高风险查询性能门禁

## 风险识别

编写或修改 SQL、DAO、Mapper、Repository、统计接口和筛选分页逻辑时，先检查是否命中任一模式：

- 先取候选页或固定批次，再按应用层计算结果过滤；为凑满一页继续向后扫描。
- 遍历全部候选对象，每个对象执行一组跨表、状态或节点查询。
- 在循环、Stream、集合映射中调用 DAO、Mapper、Repository 或远程查询。
- 为 `count`、`exists`、汇总或去重加载完整明细到应用层。
- 跨库或跨服务结果在应用层连接，且候选规模没有硬上限。
- 持续增长表上的聚合、去重、排序缺少时间、租户、组织、主键范围或其它高选择性边界。

命中不等于方案必错，但必须暂停直接落码，先完成风险回显和方案比较。不得用“每批只有 500 条”掩盖最终仍遍历全部候选的事实。

## 风险回显

至少给出以下信息；未知项明确写“待测”，不能省略：

| 项目 | 要求 |
|---|---|
| 候选规模 | 当前典型值、峰值或可验证的数据范围 |
| 批次大小 | 单批条数以及是否最终遍历全部批次 |
| 单候选代价 | 每个候选触发的 SQL、远程调用和主要关联表数量 |
| 最坏调用数 | 用公式表达，例如 `ceil(候选数 / 批次大小) × 批次查询 + 候选数 × 单候选查询数` |
| 调用频率 | 在线请求、定时任务、离线导出或一次性运维 |
| 主要风险 | 全扫、N+1、排序、临时空间、网络往返、连接池占用或超时 |

先向用户明确说明风险和推荐方案。只有证据表明现状可接受，或用户知情接受风险且补齐硬上限、超时、降级和观测，才能保留扫描方案。

## 优化顺序

按以下顺序选择最小可行方案，不要求为了优化盲目重构：

1. 将可表达且语义稳定的条件下推到数据库，在过滤后执行原生分页。
2. 把逐项查询改成集合查询、条件聚合、窗口函数、批量 `IN` 或临时结果集合，消除 N+1。
3. 对昂贵且频繁使用的派生结果增加可维护的持久化字段、汇总表、物化视图或搜索索引，并定义更新一致性。
4. 将确需全量遍历的任务改为受控异步统计或离线导出，限制并发、批次、总量和运行窗口。
5. 仅在前述方案不可行时保留应用层扫描，并设置最大候选数、查询次数预算、超时、取消、降级和指标告警。

不得为了消除全扫而无依据地增加索引。先核对 DDL、过滤选择性、表增长速度和写放大成本。

## 验证门禁

高风险查询落码前优先取得以下证据：

- 真实请求的端到端耗时，以及完成、超时或取消结果。
- 每类 SQL 的调用次数、累计耗时、最大单次耗时和返回行数。
- 执行计划中的估算行数与实际行数、循环次数、访问路径、排序、临时空间和回表情况。
- 代表性与峰值数据规模下的分页结果稳定性。

按数据库和权限选择安全方式：

- Oracle：优先读取真实游标 `DBMS_XPLAN.DISPLAY_CURSOR(..., 'ALLSTATS LAST')`；需要实际统计时确认会话已收集 plan statistics。
- MySQL 8.0.18+：可在安全只读环境对 `SELECT` 使用 `EXPLAIN ANALYZE`，注意它会实际执行查询。
- 其它数据库：使用官方支持的实际执行计划工具；会执行写语句或制造高负载的分析操作不得直接用于生产。

无法访问可信环境时，输出“性能未验证”，附后续验证方法和未消除风险。不得把只有静态推断的高风险查询描述为生产可用。

## 允许直接实施的边界

满足以下任一条件且不存在其它风险时，可以按普通查询实施：

- 主键、唯一键或明确小集合查询，调用次数固定。
- 数据集有可信硬上限，最坏调用次数已计算且符合接口预算。
- 离线或一次性任务已有并发、超时、取消和资源隔离。
- 真实计划与计时已经证明扫描成本在当前及预期增长范围内可接受。
