# 项目知识图谱初始化与维护合同

仅在明确要求初始化、导出或维护知识图谱时采用。主入口为 init-project-docs，业务建模沿用本 Skill；普通 onboard 仍交付轻量业务概览。目标是一个可交换、可查证、可迭代的项目知识包，不是安装知识平台、另造 Runtime 或扫描全部企业数据。

## 标准与唯一来源

默认采用 RDF 1.1 数据模型和 Turtle 序列化；项目已有 JSON-LD、TriG 或其他标准 RDF 载体时沿用，不强制转换。对象与关系使用稳定 IRI；词汇和分类采用 SKOS，来源采用 PROV-O，结构约束采用 SHACL。按实际需要使用 RDFS/OWL 类、属性和关系定义，声明支持子集，不声称完整 OWL 推理能力。业务词汇按 Bounded Context 定义，不因同名合并；不将数据库表、术语概念和业务对象类型视作同一层对象。

已有业务正文、OpenSpec、接口和 DDL 继续拥有各自事实，图谱以来源引用和结构映射承接，不抄成第二套业务规则。明确交付图谱时，项目新增的结构化语义关系以 RDF 源文件为唯一维护位置，图形、搜索索引及关系库导入是派生视图。Markdown 解释用途、决策与限制，不手工复写全部关系。用户选择既有结构化元数据为源时，登记其位置与导出规则，只维护那一份；不能同时手改源和导出图。

未来探索服务消费同一知识包；导入不得重写稳定 IRI、抹掉来源或把候选自动发布。改由服务存储为权威源时需明确迁移与导出责任，不能继续双向手工维护。知识包不包含凭据或默认复制生产明细。

## 初始化路径

1. 核对实际仓库、已有知识与目标业务链，登记源码提交及未提交内容覆盖、数据库身份/Schema/采集时间、接口环境与规格版本。来源只读，知识写入仅限已授权输出位置；生成 DDL、安装服务或注册全局 MCP 不属于本模式。
2. 先形成主要业务全貌，再选一条代表链建立对象、关系、状态、规则与实现映射。定向源码、Graphify（已采用且适用时）、JDBC 元数据或现有数据库工具提供证据；不重写解析器。材料不可访问、权限不足、解析不支持和确认不存在分别记录。
3. 使用项目既有命名空间及分类；无命名空间时为本项目确定稳定 IRI 基址并记录。对象 ID 不依赖行号或展示名；同一陈述的证据更新可保留身份，改变陈述含义时建立替代关系。避免将可变分支链接作为唯一版本证据。
4. 将抽取观察与业务推断分开，使用下方陈述合同记录证据。冲突保留双方来源，未知不得补造。只有开发核对、业务确认或已接受规格分别覆盖其责任范围时，才提升对应结论的确认状态。
5. 完成 RDF 解析、SHACL、来源与问题回验，交付实际覆盖的知识包和可读视图。图数与文件拆分按内容选择；无业务证据时交付缺口，不复制示例伪装真实图谱。

## 最小交付大纲

沿用现有目录；没有约定时使用 docs/knowledge/，已有 docs/domain 正文继续引用。以下是逻辑产物，不强制逐项创建空文件。

| 产物 | 必须说明 |
|---|---|
| 包清单（如 manifest.json） | 合同版本、项目稳定身份、命名空间、范围、分类版本、来源基线、各源/派生产物路径与摘要、实际生成时间、前版引用、覆盖/缺口和验证状态 |
| 可读概览 | 本次理解的业务边界、主要对象和流程、代表问题与答案、证据、未决事项；引用唯一正文及图谱对象 IRI |
| RDF 知识源（如 knowledge.ttl） | 必要词汇、对象、关系陈述、来源、采集/推导活动和逐条可信度；类定义与实例分清 |
| SHACL 约束（如 shapes.ttl） | 标识、陈述三要素、来源、版本与状态等基础约束；按本期业务增加类型/基数约束 |
| 图文视图 | 从同一知识源选择业务全景、对象关系或流程视图，能定位源对象；沿用项目图源格式，保留源和实际渲染结果 |
| 验证与增量记录 | 验证工具与版本、输入摘要、执行结果、已确认范围、失败/未执行项、变化原因及需复核结论；可复用现有报告与 Git |

包清单是导航与基线，不复制源码、接口、DDL 或全部本体。自身摘要不递归写入自身；锁定其他产物摘要，整包版本由 Git 提交或发布标识定位。同一输入和配置未变时不空改日期、版本或标识。来源受限时保留可访问性和责任方，不以本机路径冒充其他消费者可访问的证据。

## 重要结论的陈述合同

RDF 原生三元组没有可信度。默认将重要业务结论表达为有稳定 IRI 的 rdf:Statement，同时作为 prov:Entity 关联来源；候选不直接写成已确认业务三元组。rdf:Statement 的描述本身不意味着它所描述的三元组为真。派生正式视图前先通过结构验证，并核对来源有效性和确认记录的权限；只从 accepted 且未失效的陈述派生，显式过滤状态。单独筛选 accepted 不构成审核；不要把全图 union 或推理结果当正式业务事实。

| 内容 | 表达与要求 |
|---|---|
| 陈述 | rdf:subject、rdf:predicate、rdf:object 各一个；主体/谓词使用稳定 IRI，宾语可以是 IRI 或带类型/语言的值 |
| 证据 | prov:wasDerivedFrom 指向可定位的 prov:Entity，包含 dct:source 来源位置、dct:identifier 固定版本或内容摘要；不能只写“源码表明” |
| 生成过程 | prov:wasGeneratedBy 指向 prov:Activity，记录采集/推导工具、实际时间及必要运行标识；模型自报不是核验记录 |
| 依据性质 | 套件扩展 kg:basis 为 observed / inferred；观察只证明来源中可直接核对的事实，不能自动提升为企业业务规则 |
| 确认状态 | 套件扩展 kg:status 为 candidate / accepted / deprecated；accepted 必须有 kg:review 指向确认记录及责任主体，依据性质仍保留 |
| 变化与替代 | 来源改变先标受影响结果待复核；使用 prov:wasRevisionOf 关联替代陈述或版本，撤销不删除历史来源 |

kg 命名空间 `urn:team-standards:knowledge:` 是本套件交换合同 v1 的小型扩展，不是 W3C 行业词汇。仅补标准未规定的确认状态与依据性质，不改写 RDF、SKOS、PROV 含义。SHACL 只检查结构，不能证明证据内容真实、来源可访问或审核人拥有权限。冲突、审核拒绝原因在现有核对记录中保留，不能用“高置信度”替代接受。

参考[最小 RDF 示例](../assets/knowledge-graph/example.ttl)、[基础 SHACL](../assets/knowledge-graph/shapes.ttl)及[合成证据](../assets/knowledge-graph/example-evidence.md)。示例只是解析/校验夹具，不是企业初始化数据；采用时替换示例命名空间、来源、对象与活动。已有兼容合同可保持自身表示，只需登记映射与验证方法。

## 企业探索的固定大纲

显式项目知识图谱初始化采用[企业知识大纲](enterprise-knowledge-schema.md)及其唯一 YAML 定义：全项目八视图＋每个候选限界上下文十项内容。分类是同一知识的视图，不维护八份图谱。旧 01–08 编码与 IRI 保留，新标签按 schema 的 legacy_label 映射；已采用其他标准的项目登记显式映射，不静默改名。

以企业、业务域、限界上下文组织，业务边界按证据识别。全项目请求必须逐上下文执行语义、流程规则和经营指标探索，记录缺口，样板仅用于回验。YAML 大纲不等于完整领域本体；业务类型、实例、实现映射分别表达。七层认知模型仍需权威定义，不用八视图替代。

BPMN/DMN 按实际需要引用既有模型，不声称普通图表已具备可执行语义；关系库或共享知识服务不是初始化前提。

## 验证与增量维护

使用环境已有的 RDF/SHACL 实现，例如 RDFLib + pySHACL 或 Apache Jena；不自建解析器，不默认联网加载外部 ontology/context。工具缺失时说明未执行项，在授权范围补齐，不能将语法目检写成标准验证通过。示例命令（需已具备工具）：

```text
python -m pyshacl -s shapes.ttl -m -i none knowledge.ttl
```

完成条件：RDF 可解析；SHACL 执行通过；重要结论均可定位证据与固定基线；无悬空内部引用或错误身份合并；候选与正式视图隔离；全项目还须按大纲登记全部候选上下文十项覆盖，不能只靠一个样板宣称完成；至少沿一个代表问题走通“业务答案 → 陈述 → 来源”，再检查一个未知/冲突/失败情形。外部 IRI 不因未联网访问就视作失效，需区分词汇引用和必须核查的业务来源。分别报告结构通过、来源核对、业务确认与真实导入，不互相替代。

刷新使用 Git 差异、文档修订、Schema/接口快照变化定位受影响来源和陈述；文件删除、改名、关系撤销同样纳入。数据库/API变化不能仅靠 Git 发现。只复核受影响切片，保留未变标识；候选不得因重复抽取自动 accepted。已接受结论来源失效时从正式投影撤下并标待复核，保留历史版本，验证失败保留旧的有效版本但明确其时效限制。维护者请求发布时按真实权限记录回执；文件生成不是服务发布。

没有变更监听服务时采用按需或已有作业触发，报告为手动/任务触发维护，不声称已自动持续运行。后续平台可按 manifest、IRI、来源与版本合同导入，不以消费者建表要求反向改变业务语义。

标准依据：[RDF 1.1](https://www.w3.org/TR/rdf11-concepts/)、[RDF 陈述描述](https://www.w3.org/TR/rdf-schema/#ch_reificationvocab)、[OWL 2](https://www.w3.org/TR/owl2-overview/)、[SKOS](https://www.w3.org/TR/skos-reference/)、[SHACL](https://www.w3.org/TR/shacl/)、[PROV-O](https://www.w3.org/TR/prov-o/)、[BPMN](https://www.omg.org/spec/BPMN/2.0.2/)、[DMN](https://www.omg.org/spec/DMN/1.5/)。这是一组标准的最小采用合同，不声称行业存在统一的“七层八视图”标准。
