# 从原始代码和数据库反向建模

## 输入与结果

最低输入是指定代码范围及实际数据库结构，已有只读数据库访问时再用有界样本核实。只有离线DDL也能建立结构和实现模型，运行使用情况保持待核实。没有知识库、设计、OpenSpec或完整问题清单时，可以直接开始。

先还原“系统已实现什么、数据实际记录什么”，再提炼业务对象、关系、流程、状态及规则。代码里的历史兼容、缺陷和未启用分支按实现事实记录，不能自动晋升为应当遵循的业务规则；口头流程和设计意图需要针对性确认。知识沉淀从本次证据开始，按需积累。

## 优先采用成熟工具

以下是可组合的工具分工，优先使用目标项目已有安装和连接。工具选择不授予联网数据库、安装、上传代码或执行DDL的权限。

| 工作 | 默认复用 | 输出与边界 |
|---|---|---|
| 定位代码结构、入口、调用和影响 | 已有Graphify；局部缺口用IDE导航、语言工具及`rg` | 带来源的代码关系；核实版本、覆盖和EXTRACTED/INFERRED/AMBIGUOUS等实际标签，不把推断边当业务事实 |
| 读取表、列、键、约束、视图、触发器/过程 | 已有数据库客户端/连接器；需要交互看结构时用DBeaver等现有工具 | 实际元数据、DDL及ER视图；列类型、默认值、空值等以数据库为准 |
| 批量生成数据库结构文档 | 确有批量交付需求时采用SchemaSpy等现有工具 | 自动结构说明与ER；无外键时的implied关系只是候选，需要源码JOIN及数据核对 |
| 提取SQL结构关系 | 当前Graphify版本支持时索引已导出的SQL文件 | 表、视图、函数/过程、外键及部分FROM/JOIN关系；方言、动态SQL与列级信息按实际支持核实 |
| 查逻辑关联与实际使用 | 原有Mapper/DAO/ORM、只读有界查询、已有审计/历史记录 | 来源ID、真实JOIN、状态值和反例；不进行无界全表分析或改变数据 |
| 归纳业务模型与提出疑问 | Agent交叉解释上述证据，按需要由业务人员确认 | 对象、关系、状态、规则及证据引用；不重写已有工具的解析或挖掘引擎 |

[Graphify上游](https://github.com/Graphify-Labs/graphify)提供代码AST提取及可查询图；[DBeaver ER文档](https://dbeaver.com/docs/dbeaver/ER-Diagrams/)说明现有结构的可视化；[SchemaSpy功能](https://schemaspy.readthedocs.io/en/v6.1.0/features.html)与[SchemaMeta](https://schemaspy.readthedocs.io/en/master/configuration/schemaMeta.html)区分显式及推定关系。以上链接是能力参考，实际命令由安装版本的帮助及对应Skill决定，工具之间不要求同时安装。

2026-10-15的维护核实：本机graphifyy 0.9.16有SQL提取器代码、`query/path/explain`及`extract --code-only`；帮助中的直接数据库入口是PostgreSQL，图不保留完整列级细节。实际对合成SQL试运行时返回缺少`tree_sitter_sql`，因此当次SQL解析路径未就绪，不能把入口存在当作可用性验收。此事实仅描述当次环境，不能推导其他版本或Oracle也有相同直连能力。Oracle等来源优先复用其元数据读取/DDL导出，再核对方言解析覆盖；确需SQL图提取时按项目授权补依赖，不为方法维护自动升级Graphify或创建新采集器。

## 1. 先浅查全貌，再选完整业务链

没有业务问题时，从菜单/路由、Controller或旧Action、页面表单、导入导出、定时任务、消息消费者和服务入口识别候选能力，结合数据库表族和写入聚集范围归组。Graphify社区或目录分组用于导航，业务边界按实际职责核实。

记录代码提交与工作区覆盖、数据库环境/schema、元数据采集时间及可见权限，防止把开发代码和另一版本的生产库混成同一事实。先选一条有创建、推进、结束和异常分支的业务链深挖；形成粗粒度业务全景后逐链补全，不要求先读完所有源码和列。

没有Graphify时用现有IDE、语言工具和定向源码读取起步；已经有图时先查图并核实新鲜度，不重建平行手工索引。需要建图时按安装的Graphify Skill及项目范围执行；结构提取优先本地AST，代码型输入不为此要求模型API密钥。

## 2. 从数据库识别候选对象

用数据库元数据区分主数据、业务主表、明细、关联表、状态/事件历史、投影和临时/归档表。核实主键、唯一约束、外键、类型、可空、默认值、注释、索引以及视图/过程/触发器；没有物理外键不等于没有业务关系。

例如订单主表和明细可能共同组成一个业务聚合，日志和汇总表可能是同一对象的历史或投影，带分配量的关联表可能需要独立业务概念。一张表与一个业务对象不默认一一对应，实际粒度在代码读写和样本中确认。

## 3. 沿代码还原对象怎样变化

按选定动作追踪：页面/API/导入/任务→应用逻辑→规则/校验→DAO/Mapper/ORM或存储过程→实际表。对当前对象查创建、修改、审核、撤销、作废、冲销等实际入口，区分读取、写入与派生计算。

重点核对允许状态、前置校验、写入字段、关联建立/解除、库存或金额等副作用、事务失败和重复执行处理。继续看该动作后允许发生的下一动作；只找到一个成功接口不足以还原生命周期。数据库触发器、过程、批处理和其他系统写入也进入候选来源，不能只看应用Service。

## 4. 将代码关系与数据关系互相核实

外键、Mapper/SQL JOIN、ORM关联分别记录；按同名列猜出的关系保持待核实。检查来源系统、租户/组织、复合键、类型和枚举条件，避免仅因两个ID相等便关联。

在已有授权内用少量代表性对象核对主明细对应、重复/孤儿/空关联、当前状态、相关数量/金额及历史事件。样本覆盖哪些状态明确哪些；样本中唯一不能证明全库唯一，当前记录不能证明所有历史转换合法。只读连接不可用时继续完成静态模型，将运行验证列为后续条件。

数据核实复用现有数据库工具、参数化查询和项目分页/批次约定，不为建模开发第二套数据探查框架。无需为说明模型而执行创建、审核、回滚等业务写入。

## 5. 提炼业务模型并生成能力问题

从已核实读写链归纳对象中文含义、身份与粒度、关键属性、关系基数、状态/事件、指标公式和所属业务。查询谓词往往揭示“有效”“待处理”“完成”的实际含义；计算代码揭示单位、分母、冲销及统计时点。

区分以下结论，沿用项目已有证据等级：

- 可定位的结构与实现事实：例如某接口在何种校验后写入哪些列。
- 样本/运行核实：例如指定环境和时点的对象确有这条关联或状态变化。
- 业务语义候选：例如该字段是否代表业务上认可的“交付完成”。

不预设恢复全部业务意图，也不编造完成百分比。代码未覆盖的线下操作、历史原因、同字段混用、废弃功能或多系统冲突，整理成少量具体问题交给对应负责人；独立且明确的链路继续推进。

若用户未提供问题清单，从业务动作和查询生成候选问题，如“什么条件能审核”“审核后影响什么”“剩余量怎样算”“哪些对象卡住”“什么算完成”。用这些问题反向检查模型覆盖，再进入主入口的可回答性、缺口和切片安排。

## 6. 最小产出与沉淀

复用 [问题与证据模板](../assets/templates/questions-and-evidence.md) 中的反向证据追踪，以及 [领域模型模板](../assets/templates/domain-model.md)。可以在一次答复或一份现有设计中交付：

1. 当前覆盖业务链的对象、关键属性、关系及状态/事件。
2. 关键规则、计算口径、实际代码/DDL/样本证据和覆盖限制。
3. 业务语义待确认项、负责人及后续接入/补采集需求。
4. 从当前业务链提取的能力问题及已验证、部分、未知的答案边界。

现行业务模型可在没有知识库时先交付。只有项目需要长期复用时，才将确认后的术语、规则和决策放入已有或选定的文档/知识入口；已有文档原位维护。Graphify继续拥有可再生代码关系，数据库拥有DDL与运行数据，业务知识沉淀不复制另一份全量代码或表结构索引。
