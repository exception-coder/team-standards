# 企业知识初始化大纲 V1.0

唯一机器定义为 [enterprise-knowledge-schema.yaml](../assets/knowledge-schema/enterprise-knowledge-schema.yaml)。它是团队内部版本化契约，映射成熟标准，不宣称是 W3C 的统一企业本体。资产随 Skill 安装，避免只放仓库根 `knowledge/` 导致安装后缺失；不再维护第二份 YAML。

## 固定两层，按证据发现业务边界

全项目使用 YAML 的八个视图，各候选限界上下文使用十项内容。组织导航为“企业 → 业务域 → 限界上下文 → 内容分类”，子域按需登记；系统/应用与上下文是映射关系，不把 ERP 等同于整个企业。多系统可共享同一企业身份，未知身份和归属标缺口。菜单、目录、表只能提供边界线索。

大纲定义分类；本体定义有语义的类型、属性、关系和约束；图谱保存实例、实现映射与证据。三者分别登记版本与来源，不用表目录替代业务本体。实体类型与实例使用不同标识；关系基数、状态转换条件、指标单位/时间/分母必须有依据，未知不得补齐。

本版本保留 01–08 稳定编码，将既有标签映射为新标签的历史别名。已生成项目先在 manifest 登记旧版/新版和迁移映射，不批量改 IRI、不自动复制出八份图谱。类型/关系扩展需命名空间和明确定义，不能由 AI 悄悄改核心大纲。

## 全项目执行与完成判断

按 YAML 十阶段推进：全局资产 → 系统结构 → 域/上下文候选 → 业务语义 → 流程规则 → 指标决策 → 跨域关系 → 验证 → 合并 → 验收。业务语义、流程规则、指标决策对每一个候选上下文执行，既有有效证据复用。代表样板用于端到端回验，不能抵消其他上下文未探索。

先建立上下文注册与未归属资产清单，再为每个上下文登记十项覆盖。`covered` 是在范围内有来源和产物的探索结果，不等于业务接受；空数组不等于没有该业务。未探索、部分、未找到、不适用、阻塞分别记录，未找到/不适用必须有范围和依据。无法访问的上下文也在分母中，不靠删掉范围提高完成率。上下文拆分/合并保留旧 ID 及映射，重算受影响覆盖。

完成报告分别写“资产盘点”“各上下文探索”“业务确认”“消费者验收”。有未探索/部分/阻塞或未归属资产时，报告初始化基线及缺口，不声称全项目语义完成。不能承诺仅靠现有源码查出隐含线下规则。

## 唯一源与落盘大纲

项目沿用既有目录；没有约定时使用下列逻辑布局。有既有正文则用链接/对象 ID 指向原文，禁止为满足大纲复制正文。十项可以是单文档章节，不强制十份空文件。

```text
docs/knowledge/
  manifest.json                 固定 schema ID/version/hash、资产和覆盖入口
  schema/enterprise-knowledge-schema.yaml  从套件冻结的项目版本，禁止双向手改
  enterprise.md                 企业/系统范围、八视图导航与跨域协作
  contexts.yaml                 业务域、候选上下文、状态、来源、未归属资产
  coverage.json                 全项目八视图＋每个上下文十项覆盖
  domains/<domain-id>/contexts/<context-id>/
    README.md                   十项内容的导航或章节，引用已有正文
  ontology/                     领域概念与约束的唯一源，按项目实际格式
  observations/                 可重建的抽取观察，不能覆盖审核后知识
  assertions/                   有逐条证据和确认记录的语义陈述
  evidence/                     来源基线、查询与有限快照，不含凭据
  views/                        从同源知识生成的图文与阅读索引
  validation/                   结构、来源、问题回验及引擎复用结果
```

这不是必须新建的目录全集：在 manifest 中映射实际路径即可。已有 ERP 的 `knowledge.ttl`、`project-structure.ttl` 和证据文件无需迁移后才能使用；补 schema/上下文注册/覆盖引用并逐步补内容。不能把现有 37 个菜单分组直接建成 37 个限界上下文。

YAML 公共节点字段可作为 authoring profile 或 RDF 投影视图。数组保存关系/规则/证据记录的 ID，不在节点里复制全部正文；重要关系仍引用独立陈述。`verification_status` 大写通过 YAML 的映射转换为现有 RDF `kg:status` 小写。可信度默认 null，有数字必须说明计算依据；不能替代审核。混合状态节点按陈述判定，不因一个名称已确认就确认所有关系。

## 引擎入口与最小验证

AGENTS.md 和 CLAUDE.md 在项目既有维护区引用同一项目 manifest 和被冻结的 schema；已有入口只增链接，不重写其无关规则。两个引擎都按“入口 → 范围/覆盖 → 对应上下文 → 陈述 → 证据”按需读取，不默认加载全图。不依赖宿主插件缓存绝对路径；manifest 要记录原套件来源及版本。

使用 YAML 解析器检查定义，RDF/SHACL 检查实例结构；[覆盖检查器](../scripts/validate-knowledge-coverage.py)校验固定分类、缺失上下文和覆盖依据（需要 PyYAML）。输入是 `project`、`contexts`、`rows`；每行包含 YAML 所列 row_fields，项目行 section_id 为八视图编码，上下文行 section_id 为十项编码。检查通过只证明记录完整，不证明来源内容真实。

Codex 与 Claude Code 的复用验收使用同一来源基线：各自回答一个对象关系问题、一个未知问题和一个来源已失效问题，记录所用版本/来源、答案与差异；未实际运行的引擎标未验证。不要用格式一致代替跨引擎效果验证。
