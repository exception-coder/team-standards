# 跨业务、跨项目使用

本 Skill 的方法和模板适用于有现成系统及尚无系统的业务。数据系统、知识工具和建模表示法由目标项目选择；不要求使用 Yoooni、特定数据库、OWL 或图数据库。

## 同事怎样开始

团队安装包含本 Skill 的 Team Standards 插件后，在目标业务项目中选择本 Skill，或显式输入下面的请求。插件发布、安装和宿主实际发现是三个状态；源码目录中存在文件不代表同事会话已经加载。

```text
使用 $business-ontology-modeling 分析【业务名称】。
使用角色与决策：【谁准备根据答案采取什么行动】。
典型问题：【列出当前最有价值的真实问题】。
资料与系统：【项目、设计、接口、数据库或访谈入口；没有的写没有】。
本次做到：【仅分析／保存设计和规格／按已确认范围实施】。
请识别对象、关键属性、关系、状态及指标口径；分别核实来源、接入、
口径的缺口，标明证据与待确认负责人，复用现有设计并安排问题回验。
```

例：销售业务可以输入“哪些订单还差多少没交、哪些已经承诺延期”；人事业务可以输入“哪些批准岗位仍缺人、已接受录用但未入职的人是否占编”。问题决定需要的对象、事件和规则，模型中的“完成”“可用”“缺口”均需按该业务确认。

## 分发与本地试用

优先通过团队已有插件分发流程维护一个版本。需要单独试用时复制完整 `business-ontology-modeling/` 目录，保留 `SKILL.md`、`agents/`、`assets/` 和 `references/`，不只复制主文件。目录内引用全部闭合，Team Standards 的其他 Skill 通过名称按需调用，不构成单目录试用的硬依赖。

按 2026-10-15 核实的 [OpenAI 官方 Skill 文档](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)，Codex 项目级位置为 `<项目根>/.agents/skills/business-ontology-modeling/`，用户级位置为 `<用户主目录>/.agents/skills/business-ontology-modeling/`；跨仓分发可使用插件。其他宿主使用其实际支持的 Skill 目录。已有安装时先核对来源与版本，同名 Skill 不会自动合并。

复制后在目标宿主确认能找到名称、打开主入口和模板，再用一个业务问题试用。发现能力和自动触发受宿主版本、配置影响，未确认时可让当前 Agent 直接读取主文件的绝对路径；不把复制成功记为宿主验收。不要直接修改安装缓存作为团队源码。

## 复用现有规范

目标环境存在以下 Team Standards Skill 时按任务使用；只有触及相应工作才读取，避免每次建模加载整套规范。

| 当前工作 | 复用入口 | 本 Skill 补充什么 |
|---|---|---|
| 核实存量业务与术语 | `business-logic-orientation` | 将当前实现追踪到问题需要的概念和关系 |
| DDL、SQL、状态及运行数据 | `backend-evidence` | 用来源、接入、口径三个维度说明可回答程度 |
| 已授权修改行为、准备实施 | `change-readiness` | 提供问题、对象、规则和切片依据，消费项目现有OpenSpec/设计合同 |
| 方案范围和复杂度取舍 | `architecture-reasoning` | 优先能独立回答业务问题的最小闭环 |
| 概设详设与对象图表达 | `clear-design-docs`；绘图按需 `architecture-diagram-design` | 模板嵌入原有设计，保持对象粒度和关系一致 |
| 实施业务代码或Agent工具 | `architecture-ddd-lite-fullstack`、编码规范；涉及LLM时 `llm-agent-coding-standards` | 模型语义交给所属领域实现，工具复用已确认查询合同 |
| 保存、验证、提交 | `markdown-writing-standards`、`delivery-verification`、`git-commit-standards` | 用原业务问题回验，保留真实接入、人工确认和发布边界 |

这些入口缺失时，遵从目标项目已有等效规范，保留来源与推断、身份/粒度、规则/事实、未知/零值的区别。不自行补装工具、创建治理配置或宣称某个检查通过。

## 按可用证据选择路径

| 项目条件 | 使用方法及限制 |
|---|---|
| 有新鲜 Graphify | 用其定位实现和影响，再定向核实业务含义；图谱不能证明实时业务事实 |
| Graphify 缺失或过期 | 定向读取接口、源码、已有测试，说明覆盖；不为了建模默认重建全仓图谱 |
| 有 OpenSpec | 区分主规格、活动变更与实现；按实际schema更新匹配change，已完成切片再同步现状 |
| 没有 OpenSpec | 复用一份现有设计/需求合同；不因此阻塞分析，也不自动初始化 |
| 有领域知识服务 | 按项目声明解析权威来源，稳定语义与草稿区分，保留冲突来源 |
| 没有知识服务或业务尚无系统 | 用制度、业务访谈和样例建候选模型，指定语义确认人；接入状态可标“尚无实现” |
| 只有表结构或截图 | 限定可证明内容；列出待核实关联、口径和运行事实，不生成猜测SQL或全量业务结论 |

## 模板落位

三个模板是工作材料，按问题选用相关章节：

1. [问题与证据](../assets/templates/questions-and-evidence.md)：确定范围、真实问题、问题到证据的追踪和独立缺口分类。
2. [领域模型](../assets/templates/domain-model.md)：补齐对象、关系、状态、规则及查询合同，引用已有权威定义。
3. [实施与回验](../assets/templates/delivery-and-validation.md)：把当前切片落到长期设计和变更工件，用真实或明确的合成输入验收。

只需要讨论时可在答复中填出必要部分。沉淀项目知识时原位维护；OpenSpec 工件仍由该项目 schema 决定，三个模板不变成新的强制工件。

## 团队维护

方法由团队工程规范维护者维护，项目对象与规则由所属业务负责人维护。新增案例只晋升跨业务有效的判断方法；具体表名、阈值和权限例外留在案例或项目声明中。修改后用 [试用场景](trial-scenarios.md) 检查适用范围和迁移行为，再按现有发布流程交付；不新增一套建模平台或门禁。

方法来源之一为 [Stanford Ontology Development 101](https://protege.stanford.edu/publications/ontology_development/ontology101-noy-mcguinness.html)：用能力问题界定和检验本体范围。本 Skill 结合实际系统证据、领域归属和分步实施形成工程工作法；具体项目仍需业务认可与运行验证。
