# 模型怎样交给业务Agent与MCP使用

先检查当前框架的实际入口、身份/范围、工具发现、输入输出和证据协议。下表是职责划分，优先落在已有资源和公开合同；不要求每个项目新增五种文件或采用某种Agent SDK、OWL引擎或图数据库。

| 产物 | 内容与消费者 | 判断边界 |
|---|---|---|
| 业务语义 | 中文术语/别名、身份、关系、状态、指标口径、来源与未决项；既有语义查询按问题给小范围上下文 | 代码图服务研发定位，运行语义图解释规则；二者都不能代替当前业务事实 |
| 可用能力与参数 | 从实际公开契约/handler生成封闭Schema，按当前可信身份发现能力 | 概念数量不等于实体或工具数量，不把数据库列自动加入白名单 |
| 业务事实 | 所属领域查询产生数量、状态、日期和问题明细，Agent调用及解释 | 数量与规则在确定性领域层；保留范围、单位、业务/刷新时间、来源引用及版本 |
| 覆盖与缺口 | 总数、返回数、分页/截断、所需来源及缺失原因 | 无匹配、未接入、不可读、查询失败、口径待定分别表达；未覆盖不归零 |
| 回验案例 | 原问题、固定输入/快照、预期事实和限制，复用现有评测入口 | 不要求唯一工具序列；结构检查、SQL执行、真实模型、业务认可和发布分别验收 |

模型应能追踪“问题→必要概念/规则→所需事实→已注册能力→领域公开合同→来源证据”。设计中出现的Tool名称不能自动进入可用清单；未实现的能力写为接入任务。已有字段说明、范围检查、引用类型和错误合同优先复用，不另造通用证据平台。

## 两个或多个Agent运行时

区分共享业务合同和独立调查编排。共享术语、可查询字段、范围/权限、确定性计算和事实DTO；预算、推理步骤、工具传输或最终表达可按运行时现状保留。

逐个核实某运行时是否真的注册语义查询、能力发现和事实工具。一个运行时已接图谱不能推定另一个也已接。缺的是适配时，优先薄适配同一handler/公开查询；不要复制业务规则，也不强制进程内调用绕经新远程MCP。

效率先通过能力分组、小语义上下文、范围内批量取数及已有合法缓存改善。模型不接收全库DDL或完整开发代码图。缓存须保持来源/规则版本、权限范围和时效一致；同快照比较答案、完整性、工具次数、输入字节及耗时，未测量前不承诺提升比例。

## MCP按缺少的职责补齐

| 已存在什么 | 优先怎么处理 |
|---|---|
| 有能力注册表、MCP server工厂 | 复用注册和handler，核实宿主认证、transport和生命周期；工厂存在不等于已对外服务 |
| 有语义查询 | 补实际需要的概念/路径或运行时适配，不再建平行“本体问答服务器” |
| 有模型但缺事实查询 | 先实现所属领域的有界只读公开合同，再按现有目录暴露；MCP不能创造缺少的数据和业务口径 |
| 返回只有文本 | 按实际客户端/SDK合同补类型化结果；Schema与领域DTO同源，兼容原文本 |
| 开发取证缺数据库连接器 | 优先成熟客户端/连接器，按项目权限补数据源身份、元数据和有界只读查询；开发凭据不能透传业务模型 |
| 有Graphify MCP/CLI | 用于开发代码查询/路径及影响，核对版本和来源；不把推断边当业务状态或授权 |

[MCP Tools规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)定义`structuredContent`与可选`outputSchema`；声明Schema后输出必须符合，兼容客户端可同时使用序列化JSON文本。annotations只是提示，服务端仍需执行输入、身份、范围和超时校验。使用项目当前SDK和客户端实际支持能力，不因建模默认升级协议。

业务写入与外部动作继续消费所属领域公开合同和现有人工确认流程；建模、图谱或MCP导出均不扩大授权。只有实际跨项目共享/多消费者等需要出现，才比较独立服务的成本与收益。
