# 技术思想文章与白皮书

适用于解释开发思想、工程体系和架构取舍的长效文章，以及用户要求提升技术文章信息设计的改写。目标是让读者理解一套思想如何落实，不把文章写成规范目录或功能清单。详细设计、操作指南与过会稿保持各自内容契约，不套用本模式的篇幅和结构。

## 先编排观点，再选择图形

先写出文章的一句话主张，再为每节确定一个核心问题。合并回答同一问题的段落；观点前置，术语首次定义后直接使用。图文不逐节点相互复述：图表达关系，文字解释原因、取舍和必要条件。

工程理念类文章可从“核心思想 → 体系架构 → 核心原则 → 执行闭环 → 持续演进”起步，根据内容调整。封面需要时只放标题、副标题和克制视觉，不重复摘要。完整 Skill 清单、命令、字段表和实施细则放回已有权威文档，用关联阅读承接；不能为缩短正文删掉关键授权、数据正确性或尚未实现的限制。

| 要表达的信息 | 优先表达方式 | 避免 |
|---|---|---|
| 架构层次、边界与依赖 | 层级、空间、细线与有语义的连接；留白表达分组 | 一个概念一个等大彩色方框、用颜色冒充关系 |
| 流程、判断与迭代 | 明确输入输出、主流程、关键决策、失败与反馈返回点 | 只有成功路径的方框串联、无语义双向箭头 |
| 思想、角色与方法的关系 | 概念关系图或结构图 | 为了统一外观强套流程图 |
| 对比、职责、原则与清单 | 原生表格和文字排版 | 截图表格、为了显得丰富而制图 |

绘图沿用[架构可视化](../../architecture-diagram-design/SKILL.md)的语义与可编辑交付要求。图数由需要解释的关系和机制决定，封面装饰不计作架构图。需要解释技术实现原理或交付业务方案时，以[技术实现设计](../../technical-implementation-design/SKILL.md)为主；本模式只辅助信息组织和视觉表达，不决定技术深度，也不能把必要调用链、状态、边界或失败机制全部移到外链。

## 视觉靠信息秩序

优先白色或极浅灰背景、近黑文字、一个品牌强调色及灰蓝辅助色。用位置、字号、字重、比例和留白区分主次；实线、虚线等记法需保持一致并说明语义。图标确有识别作用时采用同一线性家族，卡片仅用于真正独立的内容。

不默认纯黑科技风、满屏渐变或大面积彩色矩形。项目品牌和用户明确选择优先；专业感来自可理解的结构，不来自装饰数量。文档、图、表各承担一个清楚的作用，不把长段文字搬进图里。

## 改写与验收

- 先保留原稿，标记重复观点与必须保留的事实，再重组。用户明确给出压缩比例时，记录原稿、新稿和一致的计数口径；如以正文可见字符统计，排除链接地址、Markdown 标记和图片资产名，图中文字另行检查，防止把正文搬进图片“达标”。
- “压缩 35%～45%、约五节、一张架构图加一张闭环图”可作为特定文章的编辑目标，不能固化为所有文档的门禁。压缩优先删除重复解释，不牺牲必要条件或用字号变小代替取舍。
- 按实际阅读宽度检查标题层级、图中文字、线条、箭头、留白和原生表格；手机阅读不应依赖把整张宽图缩成难读的缩略图，必要时调整纵向结构。保持 draw.io 源图与预览一致。
- 发布更新沿用原文档入口，按所用发布能力验证正文、图片位置和链接。分别报告本地渲染、API 读回与浏览器视觉验收，不能互相冒充。
- 审读时检查：每节只解决一个问题；首读能抓住主张；关键关系与失败反馈清楚；普通对比保持原生排版；引用落到权威正文；图文没有重复解释。

方法参考：[Diátaxis 的解释型文档](https://diataxis.fr/explanation/)强调围绕主题建立理解并与操作参考分离；[C4 图示记法](https://c4model.com/diagrams/notation)强调关系语义、图例和可独立理解，并不规定彩色矩形风格。它们支持上述编辑判断，不提供固定篇幅或图数指标。
