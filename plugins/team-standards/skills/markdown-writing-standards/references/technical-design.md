# 图文技术设计（TDD）

用于技术实现与数据库方案的编写、精简和审读。沿用项目已有目录、编号和唯一正文；局部变更只更新受影响部分，不为使用本风格新建整套文档。

## 从图理解，到契约实现

开头简述问题、结论和范围，再在相关章节先放图、后解释条件与取舍。“先图后文”不要求读者在没有背景时猜图意。

| 读者的问题 | 优先表达 | 图后保留什么 |
|---|---|---|
| 系统由什么组成、如何协作 | C4 上下文/容器或分层架构图 | 边界、职责、关键依赖和选择理由 |
| 一次操作如何得到结果 | 流程图；跨参与方调用顺序用时序图 | 前置条件、规则、提交点、失败去向与恢复 |
| 数据属于谁、如何关联 | 核心实体关系图 | 基数、所有者、生命周期、约束落点及物理设计引用 |
| 开发具体改哪里 | 简短模块/包路径及职责映射 | 已有或拟新增的实现入口、调用者与验收场景 |

完整方案优先检查架构、流程和数据关系三个视角是否讲清；不是必须画三张图。简单方案复用已有图或简述即可，不强制 C4 四层、流程图和时序图同时出现，也不把全部 UML 图型作为交付清单。

一图一主题，静态结构、执行过程、实体关系和部署拓扑分别表达；名称与正文、接口、源码或迁移文件一致。图后解释关键条件、理由和风险，不逐节点复述。现状、拟建与待确认在容易混淆的位置标清。

## 查阅细节保持可实施

- 接口、字段、规则和异常按用途拆成短表；长文本用段落，不做满屏总表。完整字段字典归数据库方案，应用方案引用其约束并说明读写和事务，不复制两份表结构。
- 核心代码只展示解释算法、事务或扩展点所需的片段，并标明源码位置或“设计伪代码”。说明输入、输出、关键不变量和省略条件；不贴完整类，也不以省略号隐藏影响正确性的提交和恢复行为。
- 异常写触发条件、对外结果、数据状态与恢复责任；“支持重试”需交代重复副作用如何避免。验收写具体条件和可观察结果，性能目标要有规模、环境与验证方法。
- 关键设计关联已有需求、源码、接口或 DDL/迁移依据；目标方案标拟新增，证据不足标待确认。变更时同步受影响正文、源图和引用，不用更新日期代替核对。

例如同步方案不能仅凭“分页读取＋批量 upsert”承诺不遗漏、不重复：需说明分页稳定性、水位边界、目标提交与检查点的先后、失败重放语义。增量循环不能无条件回到初始化分支。这些是有相应需求时要解释的正确性条件，不是所有文档必填的同步平台章节。

## 图源与视觉

用户指定和项目约定优先。无约定时，流程、时序、ER 优先使用正文可渲染的 Mermaid；已有 PlantUML 工程沿用其工具链；需要精确布局、汇报编辑或复杂架构图时使用 draw.io。C4 是视图方法，不绑定绘图工具。不为本次风格统一批量转换已有图。

可编辑源图与 Markdown 一同版本管理；正文使用原生渲染或同源预览，并能定位源文件。截图不能作为唯一维护源，不并行维护两份手工图源。实际检查目标载体的渲染、字号、连线和裁切，缺少渲染工具时明确未验证项，不把语法检查写成视觉验收。

正式方案默认浅色、适当留白和少量语义色；代码块可用深色主题，但受发布平台能力约束，不为颜色引入自定义渲染系统。完整参考表放在相应详设，避免主稿满屏表格或缩小图中文字。

## 完成时抽查

沿一个代表场景核对“入口 → 协作 → 数据/状态变化 → 结果”，再检查关键失败路径。读者应能定位实现位置、接口约束、数据归属及验收方法。仅文案修改复用已有事实核对；模板结构检查不等于真实项目设计、数据库或模型输出已经验证。

方法来源：[arc42](https://arc42.org/overview/)提供可裁剪的内容组织；[C4](https://c4model.com/diagrams)按受众选择有价值的视图；[Eraser TDD 指南](https://www.eraser.io/guides/technical-design-doc-with-diagrams)提供图与相关正文就近组织的参考。采用这些表达原则不要求安装或购买对应工具。
