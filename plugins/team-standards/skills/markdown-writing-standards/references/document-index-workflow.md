# 文档归属与最小维护

## 按证据职责选载体

| 内容 | 默认来源与处理 |
|---|---|
| 当前文件、符号与调用关系 | 新鲜 Graphify 加定向源码核实；按需查询，不维护手工代码索引 |
| 本次目标、设计、任务和行为规格 | 已启用 OpenSpec 时使用其实际 schema 工件；未启用时复用一份仓内设计 |
| 实际执行结果 | 测试、CI、Forge、数据库及运行证据；引用原始结果，不转抄成 Markdown 才算有效 |
| 稳定业务语义、决策与操作知识 | 已有领域知识、ADR、运行手册及项目说明；只同步受影响内容 |
| 日常变更历史 | Git 提交；仅按用户或项目明确要求另写日报 |

Graphify 有覆盖和新鲜度边界，OpenSpec 结构合法不证明实现正确，测试也不自动覆盖所有生产行为。三类证据协作，不宣布其他知识全部失去价值。

## 写前与写后

1. 从项目入口、已有链接或定向搜索找到同主题权威文档，优先原位更新。不要求全盘扫描个人知识库。
2. 新的共享文档默认随项目入仓；用户明确指定个人笔记位置时遵从。核对忽略状态，不擅自解除忽略或提交敏感、个人记录。
3. 完成后检查内容、引用、命令和结构。仅当已有导航受影响或新文档需要入口时维护对应链接；不强制创建 INDEX.md，也不逐层登记。
4. 取消 Phase-A / Phase-B 注册流程、强制双目录索引和默认快照。OpenSpec 自身目录及生命周期由官方协议管理，不另建平行索引。
5. 旧的 00–10、ai-ref、coding 或个人 ai-docs 可按需读取，不自动更新整棵树、迁移或删除。发现重复时保留独有知识与现有链接，再按授权范围处理。

## 不制造交付文档

简单 Bug 使用诊断结论、回归结果与提交正文；复杂、高风险、反复发生或用户要求的问题，复用已有问题记录，必要时才建报告。普通现状分析在会话中交付；明确需要长期基线时只维护一份有范围、证据和适用边界的文档。

机器治理文件是范围和证据引用的结构化索引，不能替代真实验证，也不能要求为了引用而新写一份报告。外部平台的规划账本、状态契约和合规留存若有明确用途，仍按对应协议维护。
