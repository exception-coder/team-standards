# 文档归属与最小维护

## 按证据职责选载体

事实来源与覆盖边界统一遵循[工程宪法的证据分工](../../change-readiness/references/engineering-principles.md#证据分工)。文档维护只补所属载体的独有知识；采用 OpenSpec 时使用实际 schema 工件，未采用时复用已有仓内设计。

## 写前与写后

1. 从项目入口、已有链接或定向搜索找到同主题权威文档，优先原位更新。不要求全盘扫描个人知识库。
2. 新的共享文档默认随项目入仓；用户明确指定个人笔记位置时遵从。核对忽略状态，不擅自解除忽略或提交敏感、个人记录。
3. 完成后检查内容、引用、命令和结构。仅当已有导航受影响或新文档需要入口时维护对应链接；不强制创建 INDEX.md，也不逐层登记。
4. 取消 Phase-A / Phase-B 注册流程、强制双目录索引和默认快照。OpenSpec 自身目录及生命周期由官方协议管理，不另建平行索引。
5. 旧的 00–10、ai-ref、coding 或个人 ai-docs 可按需读取，不自动更新整棵树、迁移或删除。发现重复时保留独有知识与现有链接，再按授权范围处理。

## 需求与迭代方案的归属

- 新需求先识别所属项目、迭代及需求，查该项目的导航、已有方案和约定目录，确认当前版本及本次影响；不同项目不得共用或猜测目的地。跨项目需求说明各项目职责和已有入口；确实无法判断归属时先核实，不阻塞其他已明确的工作。
- 沿用项目已有的“项目 → 迭代 → 需求”组织方式：一个迭代可以收纳需求1、需求2及后续需求，分别可通过名称或既有编号找到范围、方案、状态和验收；同一迭代优先复用同一目录和索引，不为每个需求强制新建目录或全套文档。没有这种结构时尊重项目现有约定，独立迭代可按“日期＋主题”等约定追加；小改动可直接更新所属正文。
- 依据实际范围依次组织需求、功能清单、必要的页面与技术设计、过会、实施和验收；复用已有资料和编号。迭代稿标明范围、状态及与现行方案的关系；没有会议决定或验证时不能写成已定或已交付。
- 更新既有项目导航和需要维护的迭代入口，能找到本次需求、当前权威方案、功能清单和可编辑图；导航只指路，不复制规则正文。确认后的变化回写受影响的现行文档；按实际影响同步相关清单、图与页面设计，不形成互相冲突的平行版本。
- 已授权发布到飞书或其他云端时，先核对项目目录到实际分类的完整路径。项目有二级目录约定时核对到该层。更新时确认原文档 ID 与现有附件，优先原位更新。分类无法核实时先完成本地稿，再确认缺少的路径。
- 发布后打开或读回正文，核对归属、章节、链接和配图位置。应随正文展示的图就地嵌入，源图链接供查看和编辑。移动前后核对链接与可见权限，替代附件按项目约定处理，无法核对的范围如实说明。

## 不制造交付文档

简单 Bug 使用诊断结论、回归结果与提交正文；复杂、高风险、反复发生或用户要求的问题，复用已有问题记录，必要时才建报告。普通现状分析在会话中交付；明确需要长期基线时只维护一份有范围、证据和适用边界的文档。

机器治理文件是范围和证据引用的结构化索引，不能替代真实验证，也不能要求为了引用而新写一份报告。外部平台的规划账本、状态契约和合规留存若有明确用途，仍按对应协议维护。
