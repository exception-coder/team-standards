# Markdown 编写规范

目标：文档内容准确、入口可发现、格式可阅读，维护同一主题的唯一权威正文。共同准则见[工程宪法](../change-readiness/references/engineering-principles.md)。

## 按读者选择文档

| 文档 | 读者要完成的事 | 正文重点 |
|---|---|---|
| 需求与交付清单 | 业务和研发对齐范围与交付顺序 | 问题、范围、功能、顺序和完成标准。多个页面按需用[页面交付计划](../page-delivery-plan/SKILL.md) |
| 概要设计 | 业务和技术负责人看懂整体方案 | 目标、分工、主流程、本期边界及关键取舍。需要说明关系时配全景图 |
| 详细设计 | 研发和测试实现并验收 | 流程、接口、数据、规则、异常和验收。技术实施、库表、页面交互可按需要放在对应章节 |
| 过会稿 | 与会人作出决定 | 按业务块讲方案、影响和待确认事项，引用详设。见[过会模式](../clear-design-docs/references/meeting-brief.md) |
| 接入指南（Quickstart） | 使用方或接入方独立完成首个可验证场景 | 前置条件、最小配置或调用、操作步骤、成功标志和常见故障 |
| 交接说明 | 接手方知道接下来做什么 | 当前结果、遗留事项、负责人、资料入口和完成标志。见[跨系统交接](../cross-system-handoff/SKILL.md) |

需求可与功能清单合写，概设可与详设同稿分节。已有设计按[内容契约](../change-readiness/references/design-output-contract.md)维护。过会稿提炼决策，Quickstart 从使用方操作出发，交接说明聚焦下一棒。几种用途共用事实时引用同一正文。图纸和导航随正文维护，故障分析、发布记录和验收证据按实际用途另行归档。

对外提供 SDK、API 或跨系统接入能力时，准备可查找的 Quickstart。每步写操作和可见结果，按需要补前置条件及排查方式。复制用的命令和配置以已验证版本为准。能力仍在设计时，明确哪些步骤和结果是拟定的。

## 正文写给读者

- 开头直接说明解决的问题和预期结果。方案接着讲谁负责、怎么走和本期范围。按[人话](../plain-writing/SKILL.md)用具体的人、动作和结果表达。
- Git 哈希、设计深度、任务分级、工具输出、AI 自检和内部验收流水号留在变更记录或验证证据中。需要锁定版本、复现或追溯时，在相关位置按需引用。保留会影响实现的状态、接口标识、业务编号、关键限制和验收条件。
- 正式方案用[全景图](../change-readiness/references/engineering-design-output.md#全景图与正文)解释关键关系。复杂细节放在详设或相应操作步骤。发布前逐段问它是否帮助读者理解、决策、操作或验收，删除过程说明、重复内容和无用途的模板项。

## 图解主稿与按需详查

- 动笔前确定读者要理解、决定还是动手，核对项目目录、章节约定和唯一正文。概设与过会稿先给全貌，详设承接实现契约，Quickstart 从使用方的首个场景开始；已有内容互链，不为分类再复制几份正文。
- 概设和过会采用便于逐屏讲解的图文结构：标题直接写结论，用主图表达关系、顺序或取舍，文字只补图里没有讲清的条件、难点、风险和待定事项。通常一张主图配 1～3 个要点即可；这是密度参考，不是页数、字数或图数门槛。
- 图和文字一起解释一个问题；说明贴近对应节点，颜色和箭头用于突出主线。图已表达的内容不再逐节点复述，不把长段文字搬进方框。单独阅读也应能理解关键条件，不能全靠讲解人补足。
- 基础路径先讲，扩展在触发场景下展开；框架内部标识留在参考节。配置示例说明哪些由用户填写、哪些自动生成、默认值和影响，避免让接入方先记整套参数。
- 接入指南说明使用方具体新增或修改哪些声明、配置、DTO、转换或调用代码，以及平台/框架已承担什么。先给一个最小可验证场景，再按需给变体；代码及配置只保留完成该场景所需部分。可用[Quickstart 模板](assets/quickstart.md)。
- 关键数据正确性、权限、事务、失败恢复和兼容条件在对应位置保留；完整字段字典、SQL、接口和代码按需查阅。每段只保留帮助本读者理解、决策、执行或验收的信息，基础概念无需重复教学。
- 所有新绘或改绘的方案图默认使用可编辑 draw.io，并在正文嵌入清晰同源预览；用户明确指定其他格式时遵从。发布时检查实际显示尺寸、文字与连线，不以文件上传成功代替可读性。飞书沿用项目约定的二级目录；已核实归属直接复用，不每次重问。

过会图文模板见[过会模式](../clear-design-docs/references/meeting-brief.md)，工程概设和详设模板见[专业设计入口](../change-readiness/references/engineering-design-output.md#按要解决的问题选择入口)。所谓 PPT 式表达指阅读结构，不默认另建 PPT 文件。

方法依据：[Assertion–Evidence](https://writing.engr.psu.edu/assertion_evidence_EA.html)支持结论标题与视觉证据；[Mayer 多媒体学习研究](https://bjorklab.psych.ucla.edu/wp-content/uploads/sites/13/2016/04/DDAndErrorsEnhanceLearning.pdf#page=68)支持删无关信息、重点提示和图文就近；[Diátaxis](https://www.diataxis.fr/start-here/)区分讲解、操作与参考；[C4](https://c4model.com/diagrams)按受众选择视图。以上用于指导表达，学习研究不等于企业过会的效果承诺，也未规定固定页数。

## 判断准则

- 识别所属项目、迭代和需求，从该项目入口、已有索引及目录找到所属文档，沿用现有组织方式；优先原位更新，现状基线与活动变更分别记录当前能力和目标增量。
- 只维护受影响的正文与已有导航。当前文档需要反映真实行为，提交说明与开发日志不能代替。
- 有生成来源时修改来源并重新生成；版本、路径、命令、数量、用法及语言版本按实际影响同步。
- 新需求方案的迭代归属、已有导航、云端当前版和历史附件维护见[最小维护规则](references/document-index-workflow.md)；纯措辞调整无需额外设计流程。

## 作业交付时同步文档

套件或项目改动在同一交付单元内核对文档影响，更新相关 README、规则入口、流程、索引与示例。跨仓分别维护组件和总览，总览只保留摘要与权威链接；非 Git 产物说明实际保存位置。

无文档影响时说明理由即可。交付前核对事实、标题、链接、命令和格式，再按[提交规范](../git-commit-standards/SKILL.md)处理本次范围。

## 必要约束与完成边界

标题层级连续，围栏闭合，表格列数一致，链接可达。修改 Mermaid 前读取[格式细则](references/markdown-format.md)的相关章节并验证；静态结构检查不能冒充实际渲染或内容正确性审读。

当前设计维护见[基线协议](../change-readiness/references/current-design-baseline.md)，概设详设表达用[清晰设计文档](../clear-design-docs/SKILL.md)，通用润色用[人话](../plain-writing/SKILL.md)。

## 精炼反例

- 功能行为变了，只在 dev-log 写一条：同步实际使用说明。
- 新增一篇文档就逐层新建 INDEX：维护需要的现有入口。
- 更新日期而不修正失效内容：原位修正文。
- Mermaid 围栏闭合就称图可渲染：执行对应校验，未渲染如实说明。
