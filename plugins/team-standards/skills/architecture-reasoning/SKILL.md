# 悟道：先判断现在需要做到什么程度

先确定当前要解决的问题，再决定是否增加技术组件。目标是给出能可靠交付、团队能维护的当前方案，而不是补齐理想架构。

## 决策方法

1. 用一句话说明谁遇到什么问题、需要什么结果。读取与决策有关的现状、约束和已接受方案，区分事实、假设及未决条件。不用组件名称代替需求。
2. 先检查现有 API、查询服务、数据模型或成熟工具能否满足目标。比较功能覆盖、数据正确性、访问控制、失败处理、维护与迁移成本，选择足够可靠的简单方案。最低复杂度不是最少代码，也不是跳过必要隔离、事务、幂等或恢复。
3. 新增平台、Registry、Agent、事件驱动或 Graph 时，说清当前不可缺的职责、已有方式的具体不足及维护成本。仅有“以后可能需要”“业内常用”或“架构完整”不构成实施依据；不用投票式清单替代这些判断。
4. 分清当前实施、可能后置和本次不做的内容。未来能力只写必要的升级信号及替换边界，不提前建两套实现、通用扩展框架或配置页面。阶段数按实际需要，一阶段足够就不写三阶段。
5. 升级条件尽量可观察：哪些查询或消费者增长、哪项已承诺目标无法满足、什么维护问题反复出现。没有依据时写待确认，不编造流量阈值或业务收益。SQL、Agent、Graph 是可选手段，不是固定演进阶梯；当前证据确实要求复杂方案时可以直接采用并说明原因。

## 输出与停止条件

简单问题用短段落说清当前建议、关键理由和必要升级条件；复杂方案再列阶段、依赖与取舍。保留关键前提及未知项，只有阻塞当前决策的歧义才提问。没有可信未来需求时无需编造 roadmap。

当前方案覆盖已确认目标、必要正确性要求且复杂组件有依据后，进入设计或实施，不重复开启“悟道 → 重新设计”循环。只在目标、约束或关键事实发生实质变化时重新判断。已确认选型不因本 Skill 被调用就推翻；发现问题提出有依据的最小修正。

## 与现有入口分工

- [change-readiness](../change-readiness/SKILL.md) 负责已授权开发的事实定位与受影响设计维护；只有存在方案取舍时使用本 Skill，不给每次 Edit 添加独立阶段。
- [architecture-ddd-lite-fullstack](../architecture-ddd-lite-fullstack/SKILL.md) 决定实现分层与依赖；[clear-design-docs](../clear-design-docs/SKILL.md) 把确定的设计写成可实施文档；独立找矛盾、缺口用 [reviewing-design-plainly](../reviewing-design-plainly/SKILL.md)。
- 方案判断在前，设计/实施随后，[plain-writing](../plain-writing/SKILL.md) 最后整理表达；人话不反向启动架构设计。项目另有阶段规划 Skill 时沿用同一份决策，避免生成第二份方案。
- 本 Skill 提供方法，不新增 Hook、机器 PASS、Forge 绑定或审批。使用它不授予编码、部署或修改项目配置的权限；已有任务授权仍按当前范围执行。
