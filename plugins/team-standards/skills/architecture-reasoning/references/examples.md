# 条件、判断与精炼反例

以下为条件案例，不代表真实项目现状或固定技术选型。先核实条件，再判断方案；仅在需要对照或试用时读取。

| 当前条件 | 充分判断 | 反例 |
|---|---|---|
| 表单中途退出后，在同一浏览器继续；数据允许本地保存 | 先评估现有表单恢复或本地存储，区分账号和业务对象，提交成功后清理；说明浏览器清理或故障可能丢失的边界 | 听到“草稿箱”就新增草稿表、CRUD、管理页和清理任务 |
| 草稿必须在电脑和手机之间继续编辑，或要求长期可靠保存 | 核实已有服务端保存能力，必要时增加持久化及受权限保护的恢复入口 | 为追求少代码仍只用浏览器缓存 |
| 草稿包含敏感资料，要求其他账号不能查看 | 核实共享终端、存储策略和真实访问控制；不能仅靠缓存键隔离，必要时使用服务端授权存取 | 将账号 ID 拼进本地缓存键就宣称安全隔离已完成 |
| 重要业务状态变化时需要提醒 | 先检查既有通知渠道和触发能力，明确接收人、时效与失败反馈 | 默认建设完整消息中心 |
| 关键操作需要主管确认 | 先检查已有审批或确认机制，明确权限、确认结果和状态约束 | 默认引入工作流引擎 |
| 销售需要查询新品进度，来源和权限尚未核实 | 先确认数据来源、可见范围和更新时间；已有查询足够就复用，缺失或过期明确提示 | 先堆 Agent、RAG、MCP、Registry 和 Graph，再找业务数据 |
| 每个部门需要不同筛选条件，字段和操作固定 | 在现有查询中支持受校验的配置，明确配置权限和无效反馈 | 为部门差异先建规则引擎和插件市场 |
| 已有消息队列，跨服务处理承诺网络中断后可重试并最终完成 | 复用既有异步通道、幂等和恢复能力，验证相关失败路径 | 因为追求“简单”而删除必要持久化和重试保证 |
| 用户明确选用服务端草稿，当前任务是补恢复接口 | 遵守已接受选型，按当前接口约束实施；具体风险才触发修正讨论 | 再次推翻选型，擅自替换为本地缓存 |
| 只修改现有页面日期格式，业务语义和接口保持不变 | 直接修改并做适用验证 | 重开需求分析、阶段规划或全模块设计 |

## 人工试用

选择实际发生的请求，核对是否识别业务结果、必要约束、已有能力和当前设计理由，以及是否擅自扩大或缩减需求。重点做成对比较：同浏览器改为跨设备，普通数据改为敏感数据，候选实现改为用户已明确选型；事实变化后，推荐方案应相应变化。

沿用实际任务记录或提交证据即可，不为试用新建平台或固定样本配额。结构校验、关键词命中和标题齐全不证明判断质量；未做独立 Agent 或业务项目试用时如实说明。
