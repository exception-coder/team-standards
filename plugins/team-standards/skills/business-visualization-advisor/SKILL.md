# 业务洞察与图表看板顾问

回答：用户要做什么决策、什么最值得看、指标如何计算、是否需要图、选什么图、放在哪里、如何进入处理明细。自动探索是开发与设计阶段的 Agent 工作流；除非任务明确要求运行时推荐引擎，不额外建设平台、引入 LLM 服务或更换图表库。

## 1. 从业务问题取得证据

- 实施前必须在当前回复或既有设计中明确四项业务目的：谁使用看板、要发现什么、发现后采取什么行动、首屏必须回答哪个问题。先从现有规格、页面和代码推导并注明依据；只有不能推导的关键项才询问用户，未明确前不进入依赖该目的的页面实施。运营关注待办与异常，管理者关注目标与结构，分析者关注比较和钻取；不要所有角色共享一套默认大屏。
- 涉及指标来源、SQL、状态或聚合事实时使用 [backend-evidence](../backend-evidence/SKILL.md)；术语或已有业务含义不清时使用 [business-logic-orientation](../business-logic-orientation/SKILL.md)。它们提供事实，本技能负责信息设计，不复制后端规则。
- 主动查找已有领域说明、已接受规格、对象模型、状态枚举与转换、接口及聚合查询、当前页面、现有指标和设计资产。项目有 Graphify/OpenSpec 时沿用它们的事实入口，再定向核实，不创建平行索引。
- 在授权范围内读取必要样本与聚合证据，记录来源、时间范围、更新时间、过滤范围、权限范围、对象粒度与采样限制。不要把分页列表当全集，不推断没有拿到的真实数值。
- 区分已证实语义、待确认假设和无法计算的候选。关键口径冲突只询问不可推断的部分，继续完成不受影响的设计。没有真实数据时交付有明确示例标记的设计和接入缺口，不能把样例当作业务洞察。

## 2. 建立最小业务语义与指标契约

复用现有契约，在当前设计载体中补齐必要信息即可，不强制新建 Metric Registry。

- 对象：唯一标识、计数粒度、主子表关系、有效/删除/归档规则、组织或租户边界。
- 状态：代码与业务名、初始/处理中/完成/取消等实际含义、合法转换、可逆/重开/重复流转、终态和截止条件。生命周期状态与“超期、未归属、风险”等可重叠标签分开。
- 时间：创建、发生、入账、到期、完成、快照和状态进入时间各自含义；注明时区、自然日或工作日。不能用更新时间代替状态进入时间。
- 指标：业务问题、名称、单位、去重键、计算式或可信指标引用、纳入/排除条件；比例还要有分子、分母及零分母行为；注明时间字段、时间粒度、比较窗口、权限范围和明细入口。
- 真实性：区分当前存量与期间流量、对象数与事件数、金额与数量。关联后先解决重复计数；混合币种先明确转换依据。缺失值与零不同，未知状态显式展示。
- 派生状态必须由业务规则支持。例如超期要同时满足“有效的未完成业务实例、适用截止时间已过、未被取消/豁免”，不能只判断日期；复借按借用实例判断。没有历史事件/快照不能推导过去在库量、状态停留时长或转化率。

## 3. 先发现洞察，再筛选候选

按任务需要执行：数据画像 → 语义核实 → 指标候选 → 洞察候选 → 约束选图 → 看板编排。

数据画像关注唯一性、缺失率、分类基数、有效时间点、时间覆盖、分布与极端值。优先探索当前规模与健康、未完成负担、超期与临界到期、状态停留与瓶颈、组织归属与集中、可比较趋势。只有数据确实支持时再探索漏斗、相关性和预测。

每个候选注明业务问题、支持证据、可采取行动、数据限制、可用表达方式。以业务重要性和可行动性优先，再比较证据质量、视觉适配和新鲜度；用高/中/低及理由通常足够。需要自动排序时才定义可解释评分，权重是项目可调策略，不能伪装成统计置信度。

先剔除口径不成立的候选，再排名；关键业务告警独立于普通排名保留，未知或过期数据不能显示为健康。去掉重复表达同一结论、没有决策用途或挤占核心任务的指标。不为凑数量遍历所有字段。统计异常要有样本、基线和方法证据；集中不自动等于异常，相关不等于因果。

### 看板优化的实施前门槛

用户要求优化统计总览或看板，或要求业务图表化改造时（不要求用户点名本技能），编码前必须读取选图规则，并形成用户可见的候选可视化清单。不能把“优化展示”提前收窄成布局调整，也不能以“读过规则”代替实际选图决策。

- 每个核心区域必须建立“业务目的 → 判断指标 → 展示方式 → 行动入口”的映射，附当前口径/数据依据。行动可以是筛选、样本明细、对象详情或授权的处理流程，不要求点击即修改数据。缺少有效行动入口的图表原则上降为辅助；确属只读监测或管理决策的核心指标，必须注明它支持的具体决策和后续处理路径，不能用“仅供参考”空泛豁免，也不能伪造路由。
- 覆盖本次范围内的现有核心指标与探索发现的相关候选，不遍历所有数据库字段。逐项记录现有表达、候选图表、最终采用与未采用项、各自理由，以及当前数据是否足以支持其语义；将结果关联上述业务目的映射。
- 每项明确选择“采用/改变图表（注明图种）”“保留数字卡”或“不画图（注明摘要、表格、明细或省略）”。即使最终保留原图，也要记录比较过的候选和保留理由。无证据的指标标为待核实，不输出真实数值。
- 清单放在当前回复或已有设计/变更载体中；多图规格复用 [Dashboard Spec](references/dashboard-spec.md)，不另建重复报告。
- 如果最终没有新增或实质改变图表，编码前向用户说明候选被舍弃的原因、为何保留原图或无图更合适，以及实际将完成哪些信息架构/交互改进。只改颜色、间距、排序或卡片位置不算图表化改造。此处要求说明，不增加例行审批；已有授权内可继续实施。
- 本门槛要求完成探索和可追溯决策，不要求一定新增图表，不降低真实数据与选图约束。纯样式修复仍按原触发边界处理。映射、候选或数据支撑判断缺失时，先补齐再实施，不能用原则性表述代替具体结果。

## 4. 选择表达与编排看板

选图与审查时读取 [图表选择规则](references/visual-rules.md)。开发 Agent 负责理解与提出候选，确定性数据计算和契约检查负责数值与硬约束；不能让语言模型估算页面指标。

按“整体情况 → 需关注事项 → 变化与原因 → 可探索明细”组织，允许按受众任务调整。首屏只承载最重要的少量问题，不固定 KPI 数量或强制每区都有图。异常可以优先成为行动列表；没有合格图表时使用摘要或明细表。

- 管理看板以“目标与结果 → 差距与风险 → 原因分解 → 行动明细”为候选层次：目标需有负责人认可的口径与期间，差距说明绝对值/比例和比较基准；原因只展示有证据的维度分解或假设，不把相关性写成归因。没有目标或同比基线就展示实际值与缺口，不编造达成率。领导关注的指标可明确优先展示，但不为制造好看结果更换分母或筛选范围。
- 标题说清业务含义，必要时附时间/单位；结论性标题必须有当前查询支持。标明“截至何时”和过滤范围。
- 同一状态跨图颜色、名称和排序一致；颜色之外有文字或符号。超期是告警语义，不把所有状态都涂成警告色。
- KPI、图与明细使用同一指标口径和过滤；点击带上状态、对象、时间与组织条件，返回保留上下文。没有可用明细能力就说明，不生成虚假跳转。
- 显示活动筛选并提供重置；零结果、无权限、部分数据、加载失败和数据过期分别表达，保留重试或恢复路径。
- 复用项目图表库、组件与设计系统；视觉一致性使用 [design-system](../design-system/SKILL.md)，页面实施使用 [frontend-excellence](../frontend-excellence/SKILL.md) 的布局、交互、可访问性与浏览器验收要求。

多图看板或跨前后端交接时读取 [Dashboard Spec 契约](references/dashboard-spec.md)，在既有设计/代码中表达可追溯规格。单张简单图只记录必要决策，不创建完整协议或通用渲染器。

## 5. 验证与交付

### 禁止浅层完成

除非用户明确只要求视觉样式调整，不能仅凭区块重排、标题修改、数字放大、卡片增加、颜色或间距变化宣称“看板优化完成”。至少证明以下一项业务能力实际改善：决策路径、洞察表达、数据比较方式、问题定位能力、行动下钻能力。布局变化可以承载这些改善，但必须用前后可观察的阅读或操作结果说明，不能把换了布局本身当成证据。没有成立的改善就继续迭代，或如实交付未完成项/仅样式成果，不能更换完成定义。

### 从业务目的反向验收

完成前必须对照四项业务目的和核心区域映射，逐项回答并提供实际证据或缺口：首屏能否发现最重要问题、能否判断问题规模、能否定位所在流程节点或适用业务维度、能否进入具体对象处理或约定决策路径、图表语义是否被当前数据支持。每项记录通过/未通过/不适用及原因；没有流程节点的对象不强加流程模型，不能用“不适用”跳过实际业务目标。关键目标未通过时不声明业务看板优化完成。

### 数据、视觉与交付证据

- 核对至少一条核心指标从原始事实/可信聚合到 KPI、图与明细的同口径结果。检查状态重叠、零分母、缺失、未知状态、重复记录、空数据、稀疏时间、长标签或高基数中与本次有关的边界。
- 实施页面后，在真实浏览器检查桌面、窄屏和矮屏：标签不截掉关键含义、图表容器能缩放、图例与明细可达、焦点可见、键盘可用，并有文本摘要或可访问数据表。不能仅靠悬浮提示读取核心数值。
- 对照实施前清单逐项核对实际图种、保留项与舍弃项；若实施发现证据不足导致方案改变，更新同一清单并说明理由。用同口径内容和相近视口比较前后效果，检查用户是否更容易读出关键差异，不能仅凭代码 diff 判断改善。
- 登录或环境阻断真实业务页时，先尝试已有授权的登录会话或项目预览机制；仍无法访问时，用真实组件与明确标记的脱敏/示例数据建立隔离预览并实际查看，或提供可查看的设计稿。不得绕过认证、暴露数据，也不得将隔离预览等同真实业务验收；没有可行预览时明确披露缺口，不声称视觉验证通过。
- 验证筛选、钻取和重置；失败或无权限不误报零值。执行与改动相关的构建/测试，不写只匹配布局类名的形式测试。
- 交付明确区分“信息架构优化”（层级、布局、阅读顺序）、“图表化改造”（新增或改变图种/数据编码）和“交互优化”，仅报告实际完成的类别，并附选图决策与可查看的视觉证据或验证缺口。
- 交付说明关键业务判断、采用/舍弃的图表及原因、已核实的数据口径、验证结果和剩余缺口。只做设计时不声称实现完成；没有真实数据或浏览器验证时明确边界。

## 6. 研究来源与采用边界

本技能依据用户提供的专家建议，将业务语义、洞察优先与可视化约束落成设计流程。2026-09-14 核对的官方参考：

- [AntV AVA 文档](https://ava.antv.vision/documentation/)：参考分析到可视化的流程，以及允许无图结果的设计。不要把历史模块架构与当前 API 混用。
- [CompassQL](https://github.com/vega/compassql)：参考候选枚举、约束、分组和排名，不默认引入依赖。
- [Observable Plot auto](https://observablehq.github.io/plot/marks/auto)：启发式选图适合探索，官方提示其行为可能变化；生产规格应明确选图结果。

具体库接入前检查项目版本与当前官方 API。专家给出的固定分数、阈值和“某图最好”是待适配启发式，不是普适事实。
