# 计划执行、验收与视图

## 领取与续接

先读取最新主清单、当前任务记录及相关提交，核对功能 ID、目标、依赖、负责人和已存在的实现。优先处理当前批次已就绪的功能。每项明确一个对交付负责的人，执行者可以是人或 AI。多人或多个 AI 协作时，按现有平台分派子任务并明确文件或职责边界，写入前确认最新领取状态。

已有实施授权时，复用项目工作流定位、实现并验证。一次推进一个可独立验收的结果，途中发现实质范围变化时回写原任务的决策与影响。外部依赖阻塞时记录原因和恢复条件，继续当前范围内已就绪的独立工作。

交接保留功能 ID、实际进展、剩余工作、阻塞、相关提交/变更和验证证据，以及下一步可执行动作。未完成的功能保留当前状态，后续执行者据证据复核，避免从头重做或跳过剩余验收。

## 状态与验收

沿用项目已有状态。无约定时可使用以下状态，阻塞原因单独记录。

| 状态 | 依据 |
|---|---|
| 待明确 | 当前目标、规则或必要依赖尚有影响实施的缺口 |
| 可开工 | 目标、验收和入口明确，前置已满足，执行责任可落实 |
| 进行中 | 已领取并开始实施，剩余工作可定位 |
| 待验收 | 当前实现可运行，仍有约定验收待执行或待确认 |
| 已验收 | 约定场景通过，证据对应当前版本和环境，项目要求的确认已取得 |

测试失败或后续变更使原证据失效时，回到相应状态并记录原因。已上线另附发布环境、版本与结果。范围取消或延期保留决定依据，进度汇总按当前承诺范围统计并标注分母。

一项功能只有部分范围就绪时，父项记录整体进展，在现有子任务或明细中标出可开工范围与未决部分。例如普通销售提交反馈可先实施，主管修改权限待确认。父项验收仍覆盖全部已承诺范围，局部通过只更新对应子任务。

页面功能通过实际入口验收，按风险核对反馈、持久化、权限、重复操作、错误恢复和必要跨模块效果。自动化结果、人工确认和 AI 判断分别注明。Mock 演示可作为阶段产出，真实服务接入的验收记录其自身证据。复用覆盖当前输入的有效验证；实施者不能通过缩减验收条件把未完成工作标为完成。

## 一个主清单，多种视图

- 有 OpenSpec 或任务平台时沿用当前任务条目，按功能 ID 或项目已有映射关联需求、设计、子任务和证据。计划页只保留索引、批次和必要说明。无现有载体时用一份仓库 Markdown 同时维护清单和明细。
- 全景图说明流程与范围，动态状态查看主清单。图中展示版本或日期，范围变化时更新对应节点和预览。
- 用户需要 Excel 时提供可筛选表格，保留稳定 ID、来源位置、导出版本/时间以及明细链接。推荐工作表为「页面功能清单」和按需要添加的「交付批次」。执行长文本留在所属正文。
- 默认把 Excel 作为导出视图。用户明确选择 Excel 为主清单时，在交付说明中登记该选择，并按 ID 关联执行明细。收到表格修改时先对照最新主清单核实差异，按范围授权回写再导出，避免覆盖较新状态。
- 工具能读取、写入或导出某种格式才执行相应操作。只有生成能力时说明快照性质，自动同步需要真实实现和验证。使用当前环境可用的表格工具及其格式校验能力，导出后核对 ID、筛选、链接、中文和换行。

## 判断示例

- 「完成待办页」细化为「销售确认待办后，状态保存，刷新后仍可见」。前端、接口和存储任务都关联这项结果。
- 同一条反馈可从客户详情和拜访记录进入，按一个功能列两个入口，并验收两条路径。
- 消息推送仍是演示时，基础待办闭环可按确认范围独立交付；真实推送保留自己的接入依赖和验收，批次承诺据此表达。

## 方法依据

按用户活动组织全景，再按能完成的目标划分交付批次，参考[用户故事地图](https://www.jpattonassociates.com/wp-content/uploads/2015/03/story_mapping.pdf)。功能清单、真实验收和续接记录参考[长任务 Agent 实践](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)。同一任务的多视图参考[GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)。采用这些方法时按本项目事实裁剪。
