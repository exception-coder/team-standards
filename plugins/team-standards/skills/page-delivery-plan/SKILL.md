# 页面功能交付计划

以角色和页面组织阅读，以用户能完成的动作组织交付。让接手的人或 AI 能找到下一项可做的工作，知道前置条件、完成标准与当前进展。共同准则沿用[工程宪法](../change-readiness/references/engineering-principles.md)。

## 确定计划依据

- 查已有需求、原型、设计、任务与当前实现，复用已核实的范围和证据。截图证明界面表达，接入、数据保存、权限及失败恢复另查对应实现或运行结果。演示数据和真实接入分别记录。
- 优先在项目现有 OpenSpec、任务平台或计划文档维护。缺少载体时按项目文档目录保存一份 Markdown 计划。主清单负责范围、状态和验收索引，详细设计与实施任务引用所属正文。登记唯一维护位置，Excel、看板和图通过功能编号关联。
- 用户指定只在聊天中讨论时，在回复中提供草案并注明主清单位置、原编号和待回写内容，落盘或绘图按用户指定时机进行。正式计划的图件与模板要求在相应交付阶段应用。
- 沿用已有功能编号。没有编号时赋予稳定 ID，跨页面的同一功能列出全部入口。共享能力列为依赖，并说明服务哪些功能。更新范围时保留原 ID、未完成承诺与变更依据。

## 拆成可交付的功能

- 按「角色 → 页面或入口 → 用户动作 → 可观察结果」拆解。每项包含实现该结果所需的页面交互、接口、权限、数据和验证，复杂技术细节引用[技术实现设计](../technical-implementation-design/SKILL.md)或[库表设计](../database-design/SKILL.md)。
- 先明确本期要打通的用户流程，再按前置依赖安排交付批次。每批写清用户能完成什么及验收范围，依赖必须在此前完成或随批次交付。当前批次细化到可以执行，后续已确认范围保留功能与启动条件。
- 一项过大时按可独立验证的用户结果拆分，子任务沿用父功能 ID 关联。前端、接口、迁移可以分派实现子任务，父功能在整体验收通过后完成。共享依赖核对复用、责任和就绪状态。
- 本批可开工项具有明确目标、验收条件、实施入口或定位办法，以及已满足的前置。缺少会改变本期行为的决策时标出待确认内容与受影响项，继续整理可独立推进部分。人员、工期和容量缺依据时保留待定，日期注明估算或已承诺性质。

## 输出与执行

用[计划模板](assets/delivery-plan.md)组织三部分，已有载体只补缺失内容。

1. **全景图**。正式计划开头用一张图串起角色、用户主流程和页面，在相关节点标功能 ID，展示本期批次及关键依赖。优先交付原生可编辑 `.drawio` 和同源预览，复用[架构可视化与表达](../architecture-diagram-design/SKILL.md)绘制、渲染和检查。局部更新复用相关图，短会话讨论按用户需要表达。
2. **页面功能清单**。一行一个可验收结果，保留编号、角色/页面、功能结果、批次、前置依赖、负责人、状态与验收链接。缺失责任人明确待分配。长规则下钻到已有设计或功能明细，避免横向堆满字段。
3. **当前批次执行与验收明细**。写入口及依据、必要实现步骤、前置与阻塞、验收场景、当前证据和下一步。按「给定条件 → 操作 → 预期结果」写适用的成功、关键失败和权限等场景。

只有规划请求时完成计划交付。已有实施授权时按[执行与视图规则](references/execution-and-views.md)领取可开工项，并经[变更实施引导](../change-readiness/SKILL.md)和[交付验证](../delivery-verification/SKILL.md)推进、回写和续接。项目已采用的 OpenSpec、Forge 与任务平台承接执行。

## 完成检查

读者能从全景图找到功能条目，再找到当前批次的执行与验收。核对主流程遗漏、重复 ID、跨页重复任务、循环或缺失依赖，以及演示、实现、验收与上线状态是否符合证据。Excel 按需提供，导出和多视图维护见[执行与视图规则](references/execution-and-views.md)。
