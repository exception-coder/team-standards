# 轻量验收与四个试画案例

用于绘图后的自检或评审，不创建评分平台、审批或 Hook。语义错误先修正，装饰不足不能成为改动架构的理由。可在既有交付说明中简短记录结果，无需新增验收文件。

## 四类检查

| 检查 | 要看的证据 | 失败时怎么改 |
|---|---|---|
| 架构准确 | 与来源核对组件、归属、方向、关键安全边界、可选性及当前/未来状态 | 修正关系或标记待确认；不能靠隐藏组件美化 |
| 表达清楚 | 标题回答一个问题，主线与阅读方向可复述，长清单已下沉 | 统一视角、减少次要文字或拆专项图 |
| 视觉可读 | 缩略图仍能识别主角与主线；实际尺寸检查统一图标、字体、对齐、留白、溢出、重叠、箭头标签与裁切 | 改构图与权重，再调整图标；不只给等大框换色或无限缩小字体 |
| 可编辑交付 | 最终 `.drawio` 全部页能打开；抽查节点改字、连接器端点、图标位置/大小/改色；预览来自相同源图 | 修复源文件后重新导出，说明未验证部分；优先自带图形，不拿整图图片替代源图，也不把逐笔画取消组合作为默认要求 |

XML 可解析只覆盖结构。截图只能证明当时的视图；源图更新后旧截图失效。交付时分别说明结构、语义、渲染与编辑抽查中实际完成的部分，不把模板自检当作真实项目验收。

新建架构说明图默认对照[已确认的团队风格](visual-language.md#团队默认风格)和最接近的模板检查主体、支撑资源、注释的主次及图标家族；已有项目规范或用户另有指定时按该约定验收。对于形象化改造，比较改前与改后：主体是否更突出、不同职责是否更易区分、图标是否同一风格、关系是否仍准确。能打开、有图标和配色统一不能单独作为“形象化已改善”的结论。标准工程图以其准确符号和可读性为准，不要求变成信息图。

图标来源与编辑深度分开核对：优先选择 draw.io 自带图形，记录实际采用的家族；已有素材不合适时再定制。内置 stencil 可能是单个可编辑图形，不能因无法取消组合就判失败或重画；只有用户明确要求逐笔画编辑时才补该项检查。

## 首批四个案例

以下是同事建议中的验证输入，不是某个数字员工产品的已验证现状。把对应模板作为试画起点，按实际来源替换；用户没有提供旧图时不宣称已完成旧图改造。

| 案例与输入事实 | 应保留的表达 | 不能出现的误画 | 模板 |
|---|---|---|---|
| 能力构成：工作能力按需组合方法、知识、工具；SOP 可选 | 工作能力为中心，Prompt、Skill、知识和 Tool 为资源集合 | SOP 成为所有能力的必经步骤；资源被串成流水线 | 01 能力构成 |
| 后台管理：公共资源统一维护，能力在员工内配置；协作可选 | 资源维护、员工配置、业务入口分区；引用和调用分清 | 入口维护公共资源；协作画成已实现且强制 | 02 系统协作 |
| 当前执行：用户逐步推动 SOP | 明确用户推动节点、权限/程序校验、结果与后续步骤 | 画成全自动规划执行；失败仍流入执行 | 03 第 1 页 |
| 未来分工：模型提出分工，程序校验通过才执行 | 明确“规划中”；规划、校验、执行、汇总；拒绝返回调整 | 模型绕过程序直接执行；未来画成当前实现 | 03 第 2 页 |

维护这项能力时，至少实际打开这三份文件的四个页面，逐项核对上述语义并抽查编辑。改了哪个页面就重验该页；不强制每次普通项目绘图重做四个案例，也不把一次通过宣称为跨工具普遍有效。
