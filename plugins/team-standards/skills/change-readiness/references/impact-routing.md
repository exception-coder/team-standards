# 按影响决定规格、设计和验证

本协议是 Agent 提交影响判断的方法。Forge 可用时，适用要求以其返回策略为准；接口、版本和旧项目兼容见[执行适配协议](execution-adapter.md)。下表用于理解影响，不在客户端实现第二套 Policy Engine。

## 独立判定

每次实施都做轻量影响判定，但不为判定另建 Markdown。复用执行记录、任务或提交说明保存证据和理由；已有 Forge 时使用其执行记录。文件数、行数和风险档位不能直接决定文档数量。

| 影响 | OpenSpec | 当前概设 | 当前详设 |
|---|---|---|---|
| 文案、样式、局部整理 | 通常无需 | 无需 | 无需 |
| 恢复已约定行为的 Bug 修复 | 引用既有规则，不建空 Delta | 边界不变则无需 | 机制改变才更新 |
| 新增、修改或移除可观察行为、权限、状态、契约 | 更新受影响 Requirement/Scenario | 流程或边界改变才更新 | 相关机制改变才更新 |
| 保持行为的大规模重构 | 可以无需 Delta，必须有行为保持证据 | 架构变化则更新 | 更新受影响章节 |
| 新模块、跨系统流程、重大数据模型变化 | 通常需要；先找既有能力 | 更新受影响部分 | 更新受影响部分 |

风险决定验证深度，与上述三个文档决定独立。重大变更必须评估规格和设计影响，不等于三类文档全部重写。一行权限变化可能需要规格；几百行等价重构可以只更新设计和回归测试。未知影响先补证据，不以“保守”为由自动生成三套文档，也不把 unknown 当无需修改。

## 探索和复用

1. 阅读正式规格、匹配的活动 change 及现行设计。以 Graphify 定位相关模块、符号、调用关系和文档，再阅读原文。
2. 图谱过期、缺失或未命中时，以定向源码/文档检索补充；缺失不等于新能力，代码事实不等于已接受行为。
3. 有匹配 Requirement 则原位映射；已有能力下新增规则使用 ADDED；修改既有行为使用 MODIFIED。只有独立新边界且排除重复后才新建 capability。
4. 需要规格变化时复用匹配 change；无需变化时不创建空 change，不因缺少概设/详设而补齐整个旧模块。
5. 需要设计维护时进入 automatic-design-maintenance，只维护受影响层次和章节；未受影响层次不为凑模板而新建。

## Forge 执行入口

`discover_execution` → 阅读返回的既有候选/活跃 change/Graphify 证据 → `assess_execution`。使用真实宿主 sessionId，输入行为影响、设计影响、风险类别、逐字原文引用和精确文件范围。Forge 保存具名 Agent 决策，不伪称人工批准。

- `preserved`：无 changeId 也可执行。理由应说明恢复哪个既有行为或为何不影响契约。
- `changed`：绑定已匹配的 change，再执行已有 `resolve_specs → confirm_spec_resolution → Delta → validate` 链路。
- `unknown`：补探索证据后再判断。
- 实施/提交前 `check_execution_readiness`；适用验证通过 `run_execution_verification` 实际运行并保存结果；原子提交后 `finish_execution` 释放写入权。
- `run_execution_verification` 只执行已授权测试，提供真实 executable/argv、测试目的及测试/配置/依赖 inputFiles；不得用于服务重启或用无断言的空命令凑 PASS。运行命令有副作用，遵守项目原有授权。

工具不可用时按同一语义人工判定，保留真实证据，不伪造机器 PASS；已启用 block 的入口仍按其明确恢复方式处理。

## 分支与任务

Agent 拆分逻辑任务并解释依赖，Forge/宿主负责分支分配和写入权。按 `session_init` 返回的执行归属恢复工作，消费 `assess_execution` 的 branch/scheduling 决策；不要把缺少 Graphify 共享节点当作并行许可。已有 Task 标识可作为 taskId 引用，真实任务顺序和完成状态仍归 OpenSpec/宿主编排器。

未接入 Forge 的兼容项目遵守项目已有分支约定：相关任务复用分配分支，以原子提交隔离；共享工作区只有一个写入会话，额外分支由宿主明确分配。本插件不实现自动依赖调度器或分支分配器。

## 验证与升级

按实际影响取验证并集：逻辑回归、API 内容/错误/权限与副作用、SQL/迁移约束、界面交互、规格 Scenario、受影响设计。区分 PASSED、FAILED、NOT_RUN 和 NOT_APPLICABLE。未执行必需检查不算通过，HTTP 200 不替代其他类型验证。

输入内容变化使覆盖它的验证失效，不能只比较 HEAD 或 git status。实施中发现新的行为、架构或文件范围时重新判定；只升级受影响轴，不自动扩大成全模块文档重写。最终检查语义覆盖，进程退出码或文件更新本身不证明业务和设计正确。
