# 方案审视：保留工程判断，按当前风险取舍

目标：在已授权范围内给出可实施、可恢复的方案。共同准则见[工程宪法](engineering-principles.md)；需求求真、最小充分和升级判断统一使用 [architecture-reasoning（悟道）](../../architecture-reasoning/SKILL.md)。本参考仅补充生产改动取舍，不设独立分析阶段。

## 适用条件

当前方案仍有实质取舍、依赖未验证假设，或沿用旧实现可能破坏权限、状态、一致性及兼容性时，按需审视。明确小改和已接受方案没有新风险时，直接实施及验证；不因出现“帮我实现”或“参考现有代码”等词语就强制重开设计。

用户的功能名或实现建议需要结合目标理解；已经明确选定的技术和能力属于当前约束。现有代码提供事实和复用线索，是否沿用取决于实际契约和维护成本。

## 生产改动准则

- **稳定与兼容**：保护真实消费者、状态和已有数据，避免无关重构。确需改变兼容边界时明确影响与过渡，不默认永久维护新老两套实现。
- **影响与恢复**：优先选择范围可控、失败可处理、结果可核实的修改。数据库和外部副作用的恢复须按实际机制判断，不能将 Git 回退等同业务恢复。
- **复用与纠偏**：保留已有业务规则和可用能力；发现与本次任务有关的结构问题时做必要修正，不扩散已知缺陷，也不借机重写全模块。
- **验证与反馈**：采用能证明相关风险受控的原生检查，必要时保留可定位失败的日志或反馈；不为每次修改额外建设可观测平台或要求全量回归。

默认按生产约束判断。只有用户或项目明确为原型、spike 或一次性探索时，才可在该范围内暂缓生产兼容及长期抽象；授权、安全、数据保护和有效验证仍成立。转入生产前补齐实际缺失保证，不新增固定“毕业审批”。

## 决策与交付

说明推荐方案、关键理由与会改变判断的条件即可；简单情况可内部判断，不强制七项回显或多方案模板。已有授权且依据充分时连续实施，只对关键业务歧义、未决选择或授权缺口请求确认。

分析咨询交付结论；已授权实施由 [change-readiness](../SKILL.md) 定位并维护受影响设计，[delivery-verification](../../delivery-verification/SKILL.md) 验证实际结果。OpenSpec 和项目门禁沿用现有采用范围，不因本参考自动启用。

## 反例

| 不恰当的处理 | 判断依据 |
|---|---|
| 看到旧代码可抄就直接扩散缺陷 | 核实当前契约与风险，复用事实和正确规则 |
| 为让补丁“更优雅”重写稳定公共路径 | 当前问题、消费者影响及较小修改的可行性 |
| 用户已接受的方案没有新问题，仍反复要求重新选型 | 当前授权与已确认约束；没有事实变化就继续推进 |
