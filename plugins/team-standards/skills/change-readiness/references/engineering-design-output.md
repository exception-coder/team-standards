# 工程设计输出规则

沿用[工程宪法](engineering-principles.md)的共同准则与证据分工。本页负责工程方案的路由、输出深度、格式和实施衔接。

## 按要解决的问题选择入口

| 设计问题 | 入口 | 正文归属 |
|---|---|---|
| 数据如何组织、存储、访问、约束和演进 | [库表设计](../../database-design/SKILL.md) | 数据所有权、模型、物理结构、索引和数据库迁移 |
| 需求如何在当前系统中实现 | [技术实现设计](../../technical-implementation-design/SKILL.md) | 模块职责、接口、执行链路、事务编排和发布验证 |
| 两者都有独立决策 | 按需组合两个入口 | 共享范围、关键决策和验收，分别维护专业内容。使用一份方案的两个小节或项目既有文档互链 |
| 只需要记录一项重要决策 | 沿用项目的 ADR 或现有方案的决策节 | 记录背景、可行选项、选择、后果与重评条件 |

将需求或方案安排成页面功能清单、交付批次与执行验收时，使用[页面功能交付计划](../../page-delivery-plan/SKILL.md)，按功能 ID 引用相关设计。

已有方案只需精简表达或独立评审时，使用 [clear-design-docs](../../clear-design-docs/SKILL.md) 对应模式。目标或方案未定且影响选型时，先用[悟道](../../architecture-reasoning/SKILL.md)收敛。维护模块长期概设或详设时，由[基线内容契约](design-output-contract.md)决定目录和生命周期，专业设计内容落在相关章节。用户明确要求的交付物和项目约定优先。

## 决定输出深度

复用项目已经核实的范围和风险，综合影响范围、存量数据、并发/异步复杂度、兼容性及失败后果，选择足以说明决策和验证的深度。写明推动升级的主要事实。影响未知时先定向核实，缺证据的关键判断标待确认。

| 设计深度 | 适用条件 | 输出 |
|---|---|---|
| L0 · 轻量变更 | 目标明确、影响局部、易恢复，例如普通可空描述字段 | 简述目标、改动、影响和验证。如需维护文档，只更新受影响的说明 |
| L1 · 局部设计 | 单模块内有一项需要说明的模型、接口或流程决策 | 短方案，说明目标、关键字段或契约、实现/迁移步骤及验收 |
| L2 · 完整设计 | 新增业务模块、复杂数据模型、跨模块协作，或局部变更存在实质的存量、兼容或恢复风险 | 概设和相关详设，关键关系/流程、数据或接口契约、适用的迁移和验证 |
| L3 · 架构级设计 | 系统级边界或核心平台调整，需权衡重要架构选项及系统性风险 | 在 L2 基础上补系统上下文、实际候选和决策、适用的容量、安全、可靠性及部署演进，标出需专项审视的决策 |

概设和详设是每类设计的深度。用户只要求概念方案时，交付目标、边界和关键决策，注明仍需细化的风险；准备实施时再展开受影响的细节。调整业务唯一性或执行不可逆迁移，即使只改一条 SQL，也要展开存量校验、兼容与恢复。这里的 L0–L3 仅描述设计输出，项目的 OpenSpec 规格深度、S/M/L 风险、架构图视图和 Forge 执行策略各按原入口处理。

## 共用格式与事实口径

独立方案优先沿用项目格式。无约定时，标题下写**设计类型、设计深度**，状态、关联需求、影响模块及版本按需要填写。正文可用**设计结论与全景图、设计范围、设计内容、关键决策、风险与约束、验证与验收、待确认事项**。L0 可直接简述，L1 可合并章节。专业模板用于组织设计内容，保留对本次决策、风险或验收有用的章节。

| 口径 | 写法 |
|---|---|
| 已确认 | 写出当前事实及可定位来源，区分需求、仓库结构和目标环境实测 |
| 设计建议 | 写明本次拟采用的行为、约束及关键取舍 |
| 待确认 | 写明缺什么证据或决策、由谁或用什么方式确认，以及影响哪一步 |
| 存在风险 | 写明触发条件、当前后果、处理措施及验证方式 |

在容易混淆处用上述标签或等价措辞，避免给每行加标签。审阅状态沿用项目约定，新方案默认草案，获得真实确认后才写已批准。设计批准、实现、验证和上线分别依据对应证据。

## 全景图与正文

- 独立交付的正式方案在开头用简短结论配一张全景图，模块概设放在「一页总览」。让读者快速看懂本期范围、主要对象、关键关系或主链路，以及与外部的边界。已有图能覆盖时直接复用，有影响时更新对应部分。L0 短说明和简单 L1 会话答复按理解需要配图。
- 库表方案突出核心实体、归属与关系，核心 ER 图可兼作全景图。技术实现方案突出入口、模块职责、上下游与结果。组合方案先给一张共用全景图，ER、时序或迁移图按需下钻。图中明确现状、本期目标与后续范围，字段明细和罕见分支留在对应章节。
- 新全景图优先用 draw.io，正文嵌入同源预览并链接可编辑的 `.drawio`。沿用用户指定格式和项目约定。绘制、打开检查及源图交付复用[架构可视化与表达](../../architecture-diagram-design/SKILL.md)。
- 正文按读者的阅读顺序写，先结论和主线，再写会影响实现的规则、决策、风险与验收。删去背景套话、对图的逐项复述和重复定义，共用内容链接唯一正文。措辞使用具体对象、动作和结果，简化时保留必要条件与异常。[人话](../../plain-writing/SKILL.md)

## 衔接实施和验收

把本期关键决策连到可实现的对象、接口或步骤，并为每项给出输入或条件、预期结果和证据获取方式。设计中写预期，实施后回填真实结果和偏差。设计咨询和独立评审按原授权交付。已有实施授权时，沿用项目的 OpenSpec、Forge 或现有任务入口，复用同一组范围和验收。实施与设计偏离时，核实影响及变更依据，更新所属正文或活动 change；交付后按[当前基线协议](current-design-baseline.md)同步已接受、已验证内容。
