# 概设与详设内容契约

开发任务自动执行[发现、补建、绑定与交付同步](automatic-design-maintenance.md)，不以 JSON 存在为前置条件。脚本负责安全合并，Agent 负责真实业务内容；只读任务不写入。

## 读者、定位与事实边界

**概要设计**面向领导、产品和技术负责人，说明业务目标、功能全景、核心流程、总体方案、范围及交付效果。首页让读者回答为什么做、给谁用、有什么功能、有什么价值、当前做到哪里。先讲业务，再解释技术边界；类名、文件路径和接口清单不能代替业务说明。

**详细设计**面向产品、研发和测试，按业务功能说明如何运行、遵守哪些规则、如何实现与验收。技术设计保留在功能技术实现及共享设计中，通过链接逐层深入。

默认每模块一份长期概设和一份长期详设，持续原位更新；已有同文件双章节绑定保持兼容，不因升级强制拆文件。不逐次生成 v1/v2/v3，不新建编码摘要或平行事实投影。绑定、切片同步与新鲜度遵循[当前设计基线协议](current-design-baseline.md)。当前正文描述已接受、已验证能力；目标、差异、取舍、任务与证据留在活动 OpenSpec change，不复制整份模块设计。

## 概设固定目录

以下八章为概设的一级业务目录。独立文档使用文档标题下的二级标题；同文件绑定“当前概设”时，相对该标题下移一级，保持顺序。每章均须有内容；标题不能替代说明。

| 固定章节 | 必须说明的内容 |
|---|---|
| 一页总览 | 目标用户、核心问题、主要能力、预期价值、当前交付状态；价值指标无依据时标待确认 |
| 业务背景与目标 | 当前痛点、建设原因、可衡量的成功标准、指标来源或确认责任 |
| 用户角色与职责 | 使用者、管理者、协作关系及责任边界 |
| 范围与功能全景 | 功能分组、本期范围、不做事项、后续候选；使用下方统一全景表 |
| 核心业务流程 | 端到端流程、角色协作、关键业务节点和异常去向 |
| 总体方案与系统边界 | 模块职责、上下游、数据所有权、关键方案及取舍 |
| 关键规则与质量目标 | 权限红线、核心约束、性能和可靠性要求；指标依据及未确认项 |
| 交付与验收 | 分期范围、验收标准、依赖、风险、待决策事项及其责任 |

功能全景表固定字段：**功能编号｜功能名称｜使用角色｜解决的问题｜主要能力｜预期效果｜交付状态｜详设链接**。编号稳定且不复用，例如 GS-001；名称使用业务语言。详设链接指向唯一功能章节。每行只能使用“规划中、实现中、已验证、已上线”之一；同功能的未交付增量另行链接活动 change，不能把整个功能升级为未验证的目标状态。

## 详设按业务功能组织

各功能以“功能编号 功能名称”为直接子标题，依次保留以下九个子章节。编号用于阅读顺序，实际标题使用下表文字，便于固定结构检查。

| 顺序 | 固定章节 | 说明重点 |
|---|---|---|
| 1 | 功能目的与适用场景 | 解决谁在什么场景下的问题，达成什么结果 |
| 2 | 角色、入口与前置条件 | 使用者、页面/触发入口、准备状态与依赖 |
| 3 | 操作流程、页面交互与结果反馈 | 正常步骤、确认、加载、空态、成功/失败与下一动作 |
| 4 | 输入输出、字段含义与校验 | 业务字段含义、来源、必填/格式/范围、返回结果 |
| 5 | 业务规则、状态转换与边界条件 | 状态前后条件、终态、组合约束和边界 |
| 6 | 操作权限与数据范围 | 哪些人能做、能看哪些对象、服务端如何约束 |
| 7 | 异常、并发、幂等与恢复 | 冲突、重试、重复请求、失败补偿和恢复路径 |
| 8 | 技术实现 | 服务职责、接口、数据、事务与外部依赖，关联实现证据 |
| 9 | 验收场景及验证证据 | 正常、异常、权限及边界的可执行输入/步骤/预期；Requirement、Scenario与真实证据 |

公共模型、通用权限、部署、迁移和兼容集中维护，由功能引用，不重复整段正文。固定结构一致，深度按影响裁剪：不适用项保留标题并解释原因，不填空模板，不用 TODO/TBD 或更新时间抵扣正文。共享设计可放详设中的独立公共章节，不挤进每个功能。适用结构图、流程图、状态图和时序图辅助理解；小改不机械要求全部图。

## 状态、同步与内容审阅

- 规划中：目标尚未实现；实现中：已有部分实现但尚未完成验收。正文必须标出状态并关联活动 change。
- 已验证：存在可追溯的验收证据，已接受切片合入当前正文。已有能力的后续目标继续留在 change。
- 已上线：除验证证据外，还须引用实际环境、制品/版本、时间、发布结果及回退信息。代码提交、测试 PASS 不能证明上线。
- 业务效果指标缺依据时写“待确认”，说明来源/责任；不能自动编造收益、提升比例、性能达标或用户认可。
- 切片交付时同步功能全景、对应功能正文和已接受主规格；归档时复核全量完整性、替代/删除功能及引用。删除功能的历史说明留在 Git/change，清理当前正文中的旧入口和关联。

每次具名内容审阅回答：业务目的与价值是否有依据、读者能否理解、流程/字段/规则/权限是否完整且一致、技术设计是否支撑验收、状态是否符合证据。记录审阅者、角色或 Agent 身份、范围、结论、问题与处理；Agent 自审不等于人工认可。

机器检查只证明结构、关联及新鲜度。字段齐全或检查 PASS 不直接等于设计合格；自然语言矛盾、业务合理性、指标真实性和设计正确性仍需内容审阅。接入与支持边界见[内容治理协议](design-content-governance.md)。
