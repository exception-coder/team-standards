# OpenSpec 概设与详设输出契约

## 1. 唯一正文与事实边界

输入为当前主规格、delta specs、已确认领域知识、既有设计与新鲜实现证据。规格定义应该怎样，概设详设说明如何组织与实现；事务、存储、异步等选择属于设计决策，记录依据和取舍，不标为既定业务真理。

优先定位现有长期正文及章节。不复制整套目录、不强制增加项目配置，不把代码清单充当设计。共享 DDL 与领域知识引用权威来源，不向项目复制一份事实。

---

## 2. 适用视图

| 产物 | 按本次影响覆盖的视图 |
|---|---|
| 概设 | 系统/领域边界、职责与数据所有权、上下游契约、核心流程、运行部署、跨切面约束、关键决策 |
| 详设 | 接口字段、权限错误、数据约束与事务、状态规则、时序异常、异步恢复与资源释放、配置兼容回滚、验收映射 |

每个视图填写 `updated`、`already-covered` 或 `not-applicable`，关联文件范围、唯一正文标题和具体理由。新接口、状态、SQL、异步、部署、安全、前端交互分别检查相应视图；多种影响取并集，包含删除、重命名及消费者。路径分类只是候选信号，审阅者须补充实际内容影响。

复杂边界、流程和交互分别使用结构图、状态/流程图和时序图；小改不机械要求所有图。遵循 markdown-writing-standards，不用空标题、TBD 或修改时间抵扣覆盖要求。

---

## 3. 按需写作提纲

首次缺少对应正文时，把适用部分写入 CLI 指定的 design 或既有长期文档，不把本提纲复制成必填空表。

1. **概设**：问题与边界 → 模块职责/数据所有权 → 上下游及公开契约 → 主流程/运行机制 → 约束与决策取舍。
2. **详设**：场景入口 → 接口/字段/权限/错误 → 状态与数据完整性 → 事务/并发/异常恢复 → 配置/迁移/兼容回滚 → Scenario 到验证的引用。
3. **Architecture Impact**：受影响文件及消费者 → 视图 → 权威文件/标题 → 更新或已有覆盖/不适用理由 → 验证入口。

---

## 4. 目标设计晋升

规划目标留在 change/design；长期正文若先写目标，明确标为尚未交付并关联 change，保留当前事实。目标与现状差异大时由 change 承载完整目标视图，长期正文只引用，验收后合入已接受部分。

每个视图确定唯一承载方式。验收后长期文档收敛为当前状态，备选与过程留在 change 或 ADR；索引及反向引用同步更新。归档前记录各视图的晋升目标或无需晋升理由，插件升级不得覆盖已维护正文。
