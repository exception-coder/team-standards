# 最小修复与回归约束

## 修改边界

- 在已有诊断证据上修复导致故障的条件；避免用吞异常、返回默认成功或未经证实的重试掩盖问题。
- 不将局部故障扩大成无关重构。需要改变接口、状态或业务语义时，回到 change-readiness 补齐设计与影响分析。
- 清理历史补丁或对齐外部实现前，确认相关行为已被替代、权威来源适用且调用方不再依赖旧分支。
- 紧急止血可先于最终根因确认，但必须说明只是缓解、适用范围和待查项；不能把症状消失当作根因已验证。

## 回归证据

1. 可自动化复现时，优先保留能在修复前失败、修复后通过的回归测试；使用独立的预期行为，不把错误实现复制成测试期望。
2. 覆盖原触发条件及相关正常路径；按实际风险补充边界、失败、并发或重复调用，不机械增加无关用例。
3. 无法稳定复现或自动测试不合适时，使用可重复的日志、数据检查或人工步骤，并记录环境、观察结果与覆盖缺口。未执行不写通过；不要为满足文档模板伪造测试。
4. 修改之后执行 delivery-verification 要求的当前验证；失败就修复或报告阻碍。新增测试本身不等于测试已通过。

## 代码与记录

编码及注释规则复用 [coding-standards-common](../../coding-standards-common/SKILL.md)，不另设 Bug 专属风格。修改同一段代码时可移除无用的旧标记或注释式旧实现，但不扩展成全仓清理；用户明确批量清理时才进入 coding-standards-common 的注释清理模式。

现象、根因、修复依据与回归结果写入本次问题的唯一载体或 commit 正文；是否需要独立报告由 [Bug 主流程](../SKILL.md) 判断。源码只保留当前职责和必要约束，不留修复历史流水。
