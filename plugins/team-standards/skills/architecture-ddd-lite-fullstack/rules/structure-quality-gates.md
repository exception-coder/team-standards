# 结构质量与改动落点

本文件补充 [DDD-lite 架构方法](../SKILL.md)，按[工程原则](../../change-readiness/references/engineering-principles.md)使用。结构服务于当前需求、可读性和正确性，不用类数、分支数或行数代替职责判断。

## 先判断是否需要调整结构

- 先找现有能力和项目实际边界；同一职责的局部修复或扩展可原位完成。
- 当规则独立变化、依赖不同、复用价值明确或现有结构妨碍验证时，提取有意义的函数、服务或适配器。
- 拆分应让变更更容易理解和验证；只增加转发层、参数搬运和文件跳转时，保留内聚实现。
- 遗留文件体积大是审阅信号，不要求每次修复都迁移整条链路。修复本次受影响问题，必要时记录后续结构风险。

### 目录即索引：按稳定语义分包

目录和 package 应帮助人和 AI 在打开文件前缩小检索范围。新增文件前先查看目标目录：若同层混放多个可稳定命名的职责簇（业务能力、外部渠道、技术适配等），复用或建立简短的语义子包，不继续堆在一级目录。包名应回答一个明确问题，例如“属于什么能力”“通过什么渠道”“用什么技术实现”。

```text
infrastructure/
  LarkMessageReceiver.java
  LarkReplySender.java
  AgentScopeConsultation.java
  ProgressQueryTool.java

→ infrastructure/lark/       # 渠道适配
  infrastructure/agentscope/ # Agent 框架适配
  infrastructure/progress/   # 进度数据适配
```

- 判断依据是稳定职责边界，不是文件数量。只有一个内聚职责簇时保持扁平；不为单个类或临时步骤造目录。
- 不为形式整齐制造 `lark/channel/inbound/handler/event/` 这类低信息量深层目录；使用足以定位职责的最短路径。
- 分包不改变层级职责与依赖方向。移动既有类时同步修正包声明、引用、测试及组件扫描，并验证行为不变。
- 编码前自检：看到目录名能否排除大部分无关文件？新增类属于现有职责簇，还是暴露了应单独命名的职责簇？

## 职责、依赖与公共边界

业务不变量在可信的业务边界落实，输入适配与外部技术细节尽量隔离。沿用项目已确认的分层；简单用例不必制造空 Domain、Repository 接口或逐层同形 DTO。

跨模块通过项目声明的公开契约调用，不穿透明确的私有边界。公开入口可以是包导出、模块 API、服务接口或 `public-api`，不统一文件命名。依赖方向由项目架构确定；不能仅因目录名含 `tool-` 就要求抽取平台。通用目录只收纳稳定且确实共享的能力，业务规则仍保留明确归属。

同一规则避免分散复制；相似几行代码尚未表达同一个稳定概念时，不急于抽象。读写对象可以按用途分开，但转换层要解决真实契约或隔离问题。

## Service 与函数的拆分依据

一个用例包含多个步骤、分支或调用并不等于多职责。优先使用清楚的命名、局部函数和直接控制流；独立业务能力再拆服务。新增分支不自动新建 Service，调用两个服务也不自动新建 Orchestrator。

| 情况 | 最小充分处理 |
|---|---|
| 同一订单校验新增一个条件 | 在现有规则中补充，复用已有测试；不为一个条件新增策略层 |
| 两种履约流程的依赖、状态与失败处理分别变化 | 按能力拆分，由现有用例选择；保持授权和事务语义 |
| 巨型服务局部字段映射错误 | 定位受影响映射并修复；仅在抽取能降低本次风险时顺带提取 |
| 多个消费者重复使用同一业务规则 | 复用所属模块的稳定能力，不为了共用搬进无业务归属的 common |

## 事务、编排与横切能力

- 用例可以组织多个服务及必要读写，关键是事务范围、幂等与失败结果明确；不能为满足层次形式打散原子性。
- 数据完整性、权限和审计保留在实际有效的边界。显式调用、框架拦截或 AOP 按项目语义选择，不统一强制拦截器。
- 测试采用能证明该风险的最小环境；纯规则可单测，事务、锁、并发或存储约束需要相应集成证据，不要求所有服务脱离事务运行。
- 不预建尚未需要的分布式补偿、消息平台或复杂扩展框架。存在已知切换需求时保留清晰边界即可。

## 评审与检查

交付时能说明本次逻辑归属、受影响依赖及验证结果即可，不逐项生成结构报告。架构路径 Hook 只识别有限命名模式，默认提醒，无法证明语义正确或替代项目 CI。项目确认规则适用后可显式开启 `block`；已有严格配置继续生效。
