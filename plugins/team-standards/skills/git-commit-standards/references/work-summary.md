# 按需工作汇总

默认以 Git 提交与真实交付证据承载工作历史，交付不自动写日报。仅查询提交或登记日志时按指定范围直接回答；周报、阶段成果或管理层汇报使用下方模式，不把模板强加给普通 Git 查询。

- 用户要求查询或汇总时，按指定项目、作者与时间读取 Git 历史，区分已提交、未提交和未验证事项，默认直接回答。
- 用户明确要求保存或项目有日志约定时，使用已有载体或指定路径；没有约定时先在当前回答提供结果，待确定持久位置后再写入，不默认创建个人 ai-docs 目录。
- 同主题合并、结果去重，不复制提交正文、完整文件清单或对话；不为日志创建 Bug/设计报告。
- 不填写虚构工时；估算必须标为估算。不迁移、删除或解除忽略既有个人日志。

## 成果价值汇报

从本期工作中筛选最值得管理者知道的成果，说明实际变化与交付风险，不追求覆盖全部事项。先事实收集，再成果识别、价值分级、主次编排，最后压缩质检；不按项目平均分配篇幅。

### 临时成果事实层

按项目、作者和周期核对 Git、用户给出的任务记录，以及项目已有的发布和验收记录。重要工作记录：项目/主题、原有问题、关键改动、能力变化、价值证据、数据及口径、来源与版本/环境、状态、成果等级及入选理由、剩余事项。新生成或要求更新提交时重查；只改同版表达时复用已核实事实与截止时间，不假称重新获取。

第一期仅在分析中整理，不新增数据库、服务、持久台账或数据接入系统；依据不足时保留未知。计划不算成果，提交标题不证明发布或实际应用，不将他人工作归为个人成果。

### 归并、分析和排序

1. 同一业务目标下的开发、修复、文档、发布合为一项成果，不同项目保留归属。按提交和语义去重，同一成果不能跨项目重复计数。
2. 分析“工作事实 → 能力变化 → 价值转化 → 交付状态”，回答原来哪里受阻、本周改变什么、现在能做什么。四层是分析方法，不是每项固定输出四段。
3. 从业务价值（流程与客户服务）、管理价值（数据透明与过程可控）、技术价值（标准、复用与稳定性）、效率价值（重复劳动与处理时间）中选最有依据的一至两类，不机械套满四类。
4. 直接说明谁能做什么、哪一步问题被解决，并匹配实际完成阶段；只有开发证据就写完成开发，不声称业务人员已经使用。真实使用、对比数据或用户反馈才支持已应用、已见效，预期用途不能写成既成效果。
5. 按下方等级先筛选，再确定重要结论、项目交付事实及关键剩余事项；重要阻碍即使没有完成成果，也应保留。核心成果与项目进展分别承担结论、证据，不重复功能清单和数字。

### 成果分级与取舍

| 等级 | 判断依据 | 默认汇报方式 |
|---|---|---|
| S | 重大业务能力上线、重要项目交付，影响关键业务目标 | 优先进入核心成果 |
| A | 重要功能建设、关键问题解决或跨项目能力接入 | 项目交付进展；本期无 S 级时，最重要的 A 级也可提炼为核心成果 |
| B | 常规优化、缺陷修复与维护 | 按共同目标合并，无独立管理信息时省略 |
| C | 命名、局部代码调整及无业务影响的实现细节 | 默认不展示 |

等级取决于业务影响、能力变化和交付重要性，不取决于代码量、任务数或提交数。只在分析中分级，不默认展示字母标签；没有 S 级或不足三项就如实少写。等级与状态独立：测试发布不能写成生产应用或已见效。按业务重要性和实际交付排序，保留用户已明确的重点项目，不机械平均分配篇幅。

### 成果和效果分别判定

| 状态 | 最低依据 |
|---|---|
| 已完成 | 开发、配置或资料工作完成，不代表运行或业务使用 |
| 已发布 | 有明确目标环境和版本的部署证据，注明测试或生产 |
| 已验证 | 有约定范围的实际验证，说明接口、模拟、真机或业务流程边界 |
| 已应用 | 有真实业务人员或真实业务场景投入使用的证据 |
| 已见效 | 有实际数据或用户反馈，量化提升保留可比基线、范围和时间 |
| 待验收 | 对应验收未完成，不否定已经通过的局部验证 |
| 待部署 | 对应能力尚未进入目标环境，不借用旧版本的发布状态 |

状态不能自动递进：本地验证可早于部署，测试发布不等于业务应用；同项目不同能力可处于不同状态。结合最新记录核对版本、环境、验证范围、开关、回滚及实际使用，证据冲突时说明不确定性。

保留有意义的业务数量、覆盖范围和可比改进，不为精简删掉关键证据，也不默认展示提交次数、代码行、源码变更文件数和测试用例数。业务文稿、日报及历史记录等数量仍保留。核对数字的对象、单位、周期、基线和完成阶段：预览不等于已发送，备份或转换准备不等于正式迁移，文件引用不等于文件内容全部可读。不推测效率提升比例。

### 面向管理层表达

核心成果每条一句“动词＋对象＋结果”，不重复背景和铺垫；结果可为可操作能力或准确交付状态，不为凑句式虚构效果。项目进展每条只讲一项成果，长句拆成一至两句短句，不用分号拼接无关成果或不同状态的任务。避免类名、接口与字段清单，不反复使用“提供支撑、奠定基础、赋能业务、提供依据”等泛化表述。优先写可观察的动作，如“三个项目已接入统一代码检查”“管理者可回查原文、核对记录”；这些表述仍须有交付证据，不能把规则修改说成真实问答效果已改善。

中文并列项用顿号，相关分句可用中文分号，独立句用句号；不以标点拖长句子。数字、单位和专有名词保持已核实原样。改稿只压缩、拆句与重排，不补充原记录未提供的信息。

默认三部分，标题注明周期与已核实的截止时间；用户本次明确格式优先，证据与筛选要求不变：

1. **本周核心成果**：最多三条最重要结论，每条一句“动词＋对象＋结果”；不复述项目段的功能清单和数字，不强凑数量。
2. **项目交付进展**：按项目或业务领域分段，每项目最多两条，每条只讲一件事，可拆成一至两句短句，不凑字数或为保留全部事项拼长句。保留入选成果的关键数据及准确交付阶段，不为精简删掉单位、范围与状态限定。用户明确要求固定模块分组时保留模块名称与归属。
3. **待办与风险**：最多四个影响交付、上线或真实使用的主题，按“项目｜未完成项（风险）｜下周动作”分栏；不适合表格时分成“未完成项”和“下周动作”两块，按项目对应。缺口与动作分开写，不藏在同一长句，也不在每个项目段后重复待完成。建议与已确认计划分开，不虚构需求、责任人或截止日期。

删除独立的“本周整体价值”及无额外信息的结尾总结，价值融入具体成果。核心成果讲结论、项目进展补事实，保持关联但不改写重述同一清单或重复数字。只汇总事实时不替用户承诺新计划；已给出的后续方向可保留，未定推断标为建议。只要本期成果、单段或固定分组时遵从用户要求，不强加待办或固定模板。

### 输出前自检

不满足就自动修订，不把清单附进周报：

1. 周期、作者及项目归属是否正确，零散事项是否按目标合并？
2. 是否先分级筛选，核心成果最多三条且未强凑 S 级或平均分配篇幅？
3. 是否用具体动作说明问题解决和能力变化，而不是任务改写或抽象价值？
4. 价值是否有事实支撑，预期与实际效果是否分开？
5. 关键数据是否保留、口径正确且未重复计数？
6. 是否区分开发、发布环境、验证范围、业务使用与实际效果？
7. 核心成果是否每条一句“动词＋对象＋结果”，项目是否每条只讲一件事并使用短句，删掉重复铺垫？
8. 核心成果是否讲结论、项目进展补事实，没有重述清单、数字或独立整体价值？
9. 待办与风险是否最多四个主题，未完成项与下周动作已分栏或分块，建议与计划已区分？
10. 是否存在虚构、夸大、混淆计划与成果，或因精简隐去的状态与风险；标点是否统一，数字与专名是否保持原样？
